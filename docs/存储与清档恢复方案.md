# 存储与清档恢复方案 v0.2

> 2026-09-08，M0必需方案收口，仅文档。本文的M0身份隔离、文件后端、写锁、持久提交、快照和凭据语义现按用户授权确定采用；实施入口为[M0实施基线](M0实施基线.md)。采用方案不等于已经实现或通过验证，本轮不启动服务、不改存档、不清档、不部署备份任务。M4玩法、M5发布/迁移/异地备份参数仍按各自阶段评审与实测，不由M0收口提前标为完成。
>
> 旧源码现状见[数据模型与接口](数据模型与接口.md)；资源语义见[事务合同](资源事务与幂等合同.md)，时钟见[恢复合同](时钟与断线恢复合同.md)。运行基线采用Node.js 24.20.0，本轮不安装运行时或依赖。

## 1. 首发存储选择与保证范围

M0确定使用一个Node进程、一个独立存储根、一个v2测试worldId和uniqueDomainId，后端为本机持久卷上的**JSON快照＋仅追加事务日志**。该根中的账号、凭据、角色、物品、业务索引和outbox属于同一持久提交域；后续跨角色交易/唯一登记也沿用它，不先拆成独立保存。M0测试账号独立，不建设跨测试/正式世界共享账号服务，不连接或自动导入旧v1存档。未来沿用账号凭据须走M5受控迁移，不能将两份正在写的根当作同一账号库。

存储根必须显式指定、规范为真实绝对路径并位于静态Web目录之外；不根据DB_HOST有无或加载失败猜后端。M0采用本地文件系统，不使用网络共享盘、两个挂载点或多进程集群共享该根。正常重启保持worldId/saveEpoch，只有明确初始化操作才允许建立不存在的世界。不是复用现有`save()`就自动具备这些保证；M0实现写入与恢复原语，M5再联验完整玩法和灾难流程。

| 目标 | 本合同承诺的语义 | 不应误读为 |
|---|---|---|
| 已回成功的钱货 | 持久提交后才回执，进程崩溃后可恢复同一结果 | 先改内存/发动画、两秒以后再尽量存 |
| 跨买家/卖家/世界 | 一次事务记录中包含全部写集合和业务索引 | 分别保存两个玩家就算原子 |
| 在线细小收益 | 每2秒的有效区间提交后才能显示已到账；未确认尾段可丢，重启不补停服 | 已显示成功的10秒收入可以随便回滚 |
| 随机与进行中状态 | 已提交种子/步骤/结果随存档回放，旧版本可恢复 | 重新调用当前随机函数模拟一遍旧战斗 |
| 磁盘/整机损坏 | 从最近可验证的异地备份恢复，说明回退范围 | 单机fsync能代替异地备份或保证灾难RPO为0 |

MySQL不进入M0实现。未来替代时必须把完整写集合、receipt、唯一索引和outbox放在同一数据库事务，并通过同一故障矩阵。禁止同一世界两后端并写、启动失败自动切空JSON，或把已有MySQL批量保存称为本合同已实现。生产存储选择记录在发布manifest，切换是独立迁移，不由环境变量的偶然缺失静默触发。

## 2. 持久卷与记录格式

以下是采用的文件职责；精确帧布局、序列化与版本号以M0实施基线为准，本轮不创建这些运行文件。权限只给服务账号与获授权备份流程，登录凭据、私信和随机根不得放在静态Web目录。M0活会话只存内存，重启全部重登，不把活会话摘要混进持久根。

| 文件/集合 | 内容 | 归属与更新 |
|---|---|---|
| `.writer-lock/owner.json` | 当前writerInstanceId、pid、hostname、processStartedAt、storageRoot真实路径 | 原子取得独占目录后写入；进程崩溃保留，不能凭年龄自动抢占 |
| `CURRENT` | 存储代际、快照名、最后快照commitSeq/hash、schema与配置manifest摘要 | 原子替换后同步父目录；不可独立于所指文件复制 |
| `snapshot.<seq>.json` | 完整规范JSON根、聚合、业务/请求摘要、outbox恢复水位 | 只写新文件，校验后发布，不原地截断旧快照 |
| `journal.<startSeq>.log` | 有长度界定与校验的完整事务帧 | 仅单写者追加；每帧完整落盘才视为commit |
| `config/<manifestId>` | 实际使用的不可变内容/经济/战斗/math配置及摘要 | 有活跃任务/订单/run引用时不可删除 |
| `history` / `receipt-archive` | 永久历史、去重压缩摘要与冷记录 | 同一逻辑事务索引，不能压缩后丢去重能力 |
| 备份manifest | 文件列表/大小/摘要、连续日志范围、worldId/saveEpoch/切点、配置和凭据版本 | 与具体备份成套；不使用“最新文件名”猜归属 |

事务帧采用[M0实施基线](M0实施基线.md)的唯一格式：4字节无符号大端头长度H＋H字节JCS头＋byteLength字节JCS正文＋固定32字节SHA-256帧尾，无额外换行。头含`formatVersion、byteLength、commitSeq、commitId、previousFrameHash、bodyHash`；bodyHash校验正文原字节，帧尾摘要覆盖前面的4字节前缀、JCS头和正文，不包含摘要自身。该摘要就是frameHash，后续帧的previousFrameHash及CURRENT的相应切点以64个小写十六进制字符引用它；最后一帧也必须独立验帧尾，不能等下一帧保护其头部。头上限4096字节，正文上限16MiB，超过上限在写前拒绝。

正文采用RFC8785 JCS规范化的UTF-8 JSON，记录操作身份、读版本、变更聚合的最终值/明确删除标记、业务唯一键、receipt终态、outbox事件和审计摘要。大整数、金额与精确小数使用合同字符串，仅安全整数可作为JSON number；拒绝重复对象键、非法Unicode及不支持的字段形状。业务名字的规范化发生在输入校验，不借JCS修改密码或名字。

字节长度与摘要针对实际保存的精确字节；恢复先有界读取/解析头以确定长度，再校验正文摘要、整个帧尾及前序链，通过后才解析并应用业务正文，不能解析后重新序列化来掩盖差异。一次帧只记录本次变动的具体聚合/索引项，不把所有账号、历史或整个根作为每次操作的after-image；重放对已标识记录安装最终值/墓碑，不把outbox重放变成再次追加奖励。完整根仅属于快照。

保存after-image和版本是为了恢复时**应用已决定结果**，不重新运行会读当前时钟、随机数或新经济参数的业务代码。删除也有tombstone/revision，不能从旧文件重新出现。全局commitSeq从0起只增，字符串保存以避免长期整数溢出；同seq不同hash或同commitId不同内容是损坏/双写，不用“后读覆盖先读”解决。

### 单写者提交顺序

1. 入口先完成认证、主体/代际、格式、体积及限流检查；进入写者后先查原requestId/payloadHash。已有同payload终态直接返回，异payload冲突，两者都不推进原业务的时间。payloadHash只含原请求明示的输入、版本和报价引用，不把当前可变服务端配置版本重新混入；注册使用独立注册作用域。
2. 对新意图采样一次serverTime，按[M0实施基线](M0实施基线.md)第6节将受影响角色/场景的合法在线区间、升级、补期和过期处理为独立durable时间前置事务（prelude）。无实际变化不写空帧；前置提交失败或未知时停止后续写，不执行玩家动作。只读回执查询不触发此步骤。
3. 前置已确认后，再比较最新controlRevision、account.revision及expectedObjectRevisions中本命令要求的版本，然后校验业务唯一键、权限、featureGate、余额/容量/资格。前置中的升级/资格变化可使请求版本过期，此时玩家意图仍未受理，但已提交的合法时间收益不回滚。
4. 只在独立工作副本中形成业务结果、随机推进状态、业务记录、receipt和outbox，检查资产守恒、引用/唯一性。成功、合法changed=false no-op和已受理权威业务拒绝分别保存自己的终态回执；业务拒绝不扣发。只有真实变化的聚合才递增版本，每次事务每个聚合至多加1；no-op/拒绝仅落回执，不虚增资源版本。
5. 完整追加业务事务帧（含32字节帧尾）并等待文件持久同步；若本次使用了新建/轮换的日志文件，先保证文件名及父目录也已持久同步。失败或结果不确定时暂停后续写入，不发布工作副本、不声称确定未扣。步骤2的前置事务采用同一持久原语。
6. 确认完整有效帧后替换已提交内存视图，更新commit水位。只有此后可以回成功和分发outbox；HTTP与SSE先到哪一个都不影响业务结果。若在持久后、内存发布前崩溃，启动回放已决定结果并返回原receipt；outbox可重投相同eventId，不再扣发。前置与业务是两个commit，双方各有真实变化时可先后递增版本。

文件写API一次返回不一定写满，实施必须处理短写并检查实际字节数；同一日志句柄写操作严格串行。日志同步失败后保持只读/维护并查询原requestId，不能边报错边继续用未确认内存接交易。单写者内所有权限/状态/余额校验与提交有同一顺序，不能在异步落盘期间让别的写意图消费尚未确认结果。

### 2.1 唯一采用的写锁与受控解锁

M0采用**原子mkdir独占锁目录**，不另引入锁服务、flock或进程内布尔锁替代。启动先解析存储根realpath，再原子创建固定`.writer-lock`目录；仅创建成功的进程可以写owner.json。owner包含随机UUID writerInstanceId、pid、hostname、processStartedAt、真实storageRoot；文件与相应目录同步完成后，才开始读CURRENT及恢复。若锁目录已存在，无论owner完整与否，第二进程均退出且不接客；PID不存在、PID重用、目录年龄和超时均不能触发自动抢锁。

正常关闭顺序为停止受理写入→排空已受理写队列→确认日志同步完成→关闭存储句柄→核对owner仍为本writerInstanceId→清除owner/锁目录并同步父目录。任何未定提交、关闭失败或进程崩溃都保留锁，不能在finally里无条件删锁。

崩溃后采取受控恢复：先停止服务及自动重启守护，确认旧写者已结束、该存储根未被另一进程或共享挂载使用；封存owner及相关故障记录，记录操作者/原因后移走锁目录并同步父目录，再启动一个新写者执行第4节完整恢复。不是只删锁即恢复服务，更不把移锁当作日志已无损的证明。M0允许这一步人工处理；故障验收须记录解锁步骤，不假设当前方案具有无人值守抢锁或自动自愈能力。

## 3. 快照、压缩与去重保留

M0采用每5分钟或新增日志达到32MiB时触发新快照，另提供受控手动快照；一次最多一个快照作业。这是实施默认值，不是已通过容量/延迟测试的承诺，也不改变每笔业务立即持久的要求。单写队列在已提交切点K取得不可变快照视图，不能异步序列化仍会被后续命令修改的活根；快照包含到K的聚合、业务索引、receipt/摘要与outbox恢复数据，K之后日志完整保留。写临时快照→同步文件→校验解析/摘要/引用→原子改名→同步父目录→发布并同步CURRENT。任一步失败继续使用原可验证快照和完整日志，不能提前删旧文件。

M0先保留全部日志与完整回执，不执行自动压缩/删除；至少保留上一个完整本机恢复集合。30天摘要压缩、旧日志回收和分层保留调度列为M5运维实现；未做压缩时继续保存完整记录，不能届满直接删除。将来只有新快照与其备份均验证覆盖到K、全部历史/去重索引可查询后，才回收被覆盖的旧日志段。不能先删日志再写快照，不能把“已发SSE”当作可以丢永久业务事件的理由。`.bak`只是一个副本，不能证明所有已回成功的交易都在其中。

| 记录 | 生命周期 / M5压缩策略 | 压缩后的最低内容 |
|---|---|---|
| 已受理命令完整回执 | 至少30天；M0不压缩，M5才可按此策略转摘要 | 主体/world/epoch/requestId/payloadHash、成功或业务拒绝、commitId、主版本、产出对象/业务键、结果摘要；在其世界历史范围内永久保留 |
| 一次任务、出生奖、成礼、课程、一次兑换、首个、唯一保管去重 | 世界历史/永久规则要求的生命周期 | 不能因回执30天过期重新领奖；永久师承用跨epoch账号对索引 |
| 日常/周常资格终态 | 压缩后保留资格ID、锁定奖励、完成/发奖周期与commit | 被耗资格不能因只保留当前周重新使用；发放高水位用于跳过已处理周期 |
| 自然小时/日周消耗账 | 当前周期与有在途引用的旧周期 | 全部在途结清后可归档；先保留汇总/截止水位再压缩明细，不能让旧run碰新周帽 |
| 在线积分/服务端tick | 单调结算锚点、尾数和必要段状态 | 不要求每2秒永久建客户端nonce行；任何重放不得退回已积分位置 |
| 普通SSE投递/重放记录 | M0采用24小时在线补读窗口；底层日志保留不等于扩大对外补读窗口 | 过窗客户端取快照/永久通知；窗口可清，不清永久业务事实 |
| 重要通知/编年史/师承/唯一历史 | 按其永久展示合同 | eventId、参与者ID与当时展示快照/公开同意、正文版本；更正追加而非改成另一件事 |

压缩后的旧请求返回`already_committed`或`already_rejected`及可查询对象/恢复指引；不能重建一个猜测的原回执，更不能重新执行。同requestId不同payloadHash始终冲突。运营磁盘容量不足时拒绝新写并告警，不把去重TTL调成五分钟来维持表面可用。

普通聊天重放窗口同样采用24小时，个人系统通知直到用户读后再按显示保留策略归档，永久事件不受影响；这些领域在其功能阶段启用，M0不因此实现完整聊天历史管理。私信/昵称/关系可见性不等于永久公开；备份与审计访问须受相同授权边界。详细UI阅读/删除流程见第6项，本轮不发送任何真实消息。

## 4. 冷启动与异常恢复顺序

1. 按第2.1节取得写者锁，进入维护状态，不先启动会写资源的HTTP/定时器；遗留锁先走受控恢复，不自动跳过。
2. 校验CURRENT、快照摘要/schema、world/epoch、所需配置及日志链。不存在任何存档且有明确create-world标记才可创建新世界；“文件读坏返回null”不能触发新号初始化。
3. 从快照K顺序重放有效事务帧K+1…N，逐帧校验正文hash、32字节帧尾、前序hash/seq、聚合预期版本及唯一约束；最后帧同样验其完整帧尾。命令业务代码与奖励公式不重跑，outbox未送可重发同eventId。
4. 仅当最后帧确为写入中断产生的不完整尾部时，保留原损坏文件副本/摘要后丢弃该尾部。完整帧校验失败、中段缺失、跳号、双uid属于需人工核查的恢复失败；不可跳过继续跑。
5. 重建位置/背包/关系索引、投影、交情下限、资格授予高水位和唯一资产引用；检查非负余额、材料绑定分量、库存占用、run终态、市场托管和receipt/业务事件一致。
6. 清除所有运行连接/lease和内存缓存。按时钟合同推进离线允许的作物/加工/周期/期限；暂停在线修行，不补停服战斗机会。需业务变更的恢复本身也提交唯一恢复事务，不能只改内存。
7. 恢复已启用领域中的进行中run、生产和交易过期/待领，未解决异常聚合隔离且可查询。M0尚未启用的集合按manifest保持空/关闭，不要求先实现M3/M4玩法；若存档已经含当前实现不支持的非空引用，应拒绝相应恢复，不能忽略后写回空集合。严重全局/唯一一致性冲突不开放相关写功能。
8. 生成恢复报告（起点/终点seq、采用文件、丢弃尾段、隔离对象、配置、耗时），达到门槛才开放请求，再续outbox；健康接口的ready须反映此阶段。

正常重启不变saveEpoch，已确认receipt能原样重放；所有会话重登/重绑角色，旧在线时间不被继承。若仅应用进程崩溃且日志仍可靠，已成功操作目标为零丢失。若从较老异地备份进行有意灾难回退，必须走下一节新的代际，而非假称“普通重启一切没变”。

## 5. v1迁移、内测与正式清档

本节都是操作方案，任何实际清档/回档仍需针对具体世界、备份和切点执行审阅，不是本轮文档请求对真实存档的删除授权。M0只实现独立测试世界显式初始化、正常重启与新旧saveEpoch拒绝隔离；不导入旧v1账号、不开放正式清档/灾难补偿/合服工具。下列跨域迁移及正式历史保留在M5执行前完成实现与演练；相关唯一玩法数据在M4才开始产生。

| 场景 | 保留 | 重建/隔离 | 身份边界 |
|---|---|---|---|
| 旧运行v1→新游戏v2 | 原账号登录名及凭据校验能力；建立一次旧名→accountId迁移映射 | 旧等级、银两、装备、地图、任务、市场/寄存、首个、编年史不导入v2角色与奖励；v1只读封存供核对 | 新worldId/saveEpoch、新characterId；不把旧背包当初始6装备的一部分 |
| M2/M3阶段内测→正式首发 | 可沿用测试者账号与凭据 | 测试角色、首个、物品、关系档/称号均留在测试世界，不冒充正式史 | test/prod不同worldId和uniqueDomainId；内测告知不继承成果 |
| 同一正式世界常规重启/补丁 | 全部已提交进度、request去重、首个、编年史、师承与唯一正本 | 只重建运行连接/缓存；配置更新不主动清玩家 | worldId/saveEpoch保持；schema/content版本可受控迁移 |
| 事先明确的正式进度重置 | 账号；world.firsts、正式编年史、永久师承/毕业与十声历代记录、反重复终身索引 | 当前等级/资产/任务/日周库存按新规则重建；旧角色链接为archived，活动邀请/市场/run先结清或封存 | 新saveEpoch、新characterId；旧进度不再可写，历史不发第二次一次奖 |
| 灾难回退到旧备份 | 备份切点以内可证明一致的数据/历史；切点后的可独立证实日志尽量补回 | 无可靠证据的期间不猜补资产；出具损失范围与后续补偿清单 | 同worldId新saveEpoch＋恢复代际，旧session/request/cursor拒绝；旧uid保留且不可二次复制 |

正式“进度重置”不能删掉唯一历史再生成第二把十声。切换前先停止写入，结清/冻结活跃战斗引用与市场/生产/run、处理托管返还账；唯一正本按已有回收合同清打造投入、归系统保管，保留原uid和唯一登记，再按公开规则重新产生本代候选。旧持有者应得凭证保留受限记录，新角色能否承接必须在重置公告中明确；默认不把旧角色可提现资产暗中搬到新角色。

历史师承不自动赋予新角色active师徒权益；新角色只显示同账号的历史关联，不能通过建立过的账号对再次毕业刷称号。新世界不承认旧v1“首个”，正式世界自身首个在进度重置后只读保留，不能每轮再争同一“历史首个”；若将来引入赛季首个须新指标/展示名，本轮不偷偷启用赛季系统。

### 清档/迁移的可审阅步骤

先产出迁移/重置清单：源与目标world/epoch、schema/config、保留/重建集合、角色/装备/挂单/唯一/历史计数与摘要、受影响进行中对象、备份位置与校验结果。冻结源写者并取得一致切点；在独立目录转换、校验外键/绑定/唯一性、重启回放和只读核对。只有目标可验证后切CURRENT/部署指向；源只读保留，转换失败继续源，禁止“半批账号已迁、半批资产还在写”。

灾难回退前先封存故障数据及所有可取日志，停止原后端与队列。恢复报告须声明最后可靠commitSeq及可能损失时段；旧客户端全部重新鉴权并取新代际快照，旧epoch命令返回SAVE_EPOCH_MISMATCH而不是当新请求。补偿只能在随后明确批准的补偿事务中按证据一次发放，不用删receipt制造“再领一次”。

## 6. 凭据保留与认证数据

旧代码使用带/不带salt的SHA-256校验，不能在迁移文档里称它等于现代密码存储。M0新凭据记录采用`{accountId,algorithm,parameters,salt,digest,authRevision}`，与账号/注册结果一起进入**服务器私密journal、快照及授权备份**，使注册、凭据更新与撤销版本能原子恢复。“不进日志”只指应用/诊断/访问日志，不包括本节必须持久化的私密事务日志；凭据不得进入角色state、SSE、公开回执或诊断信息。明文密码、邀请码与活会话token在上述所有持久载荷中均禁止出现。

M0新密码确定采用Node异步scrypt：N=131072、r=8、p=1、随机salt16字节、输出64字节、maxmem256MiB。认证计算并发固定1，等待队列最多16、单次排队最多10秒；超限/超时返回RATE_LIMITED，不无限堆积内存。账号失败尝试最多5次/60秒，IP全部认证尝试最多30次/60秒；限流先于昂贵计算且独立于资源写队列。M0不信任客户端任意X-Forwarded-For，默认以socket来源地址计IP；以后经反向代理部署须先配置明确可信代理边界。参数现用于开工，实现时仍须实测延迟与资源使用，不能把采用值称为认证压测已通过。Node官方提供异步scrypt，随机salt至少16字节，且maxmem须覆盖内存成本。[Node.js crypto 文档](https://nodejs.org/api/crypto.html#cryptoscryptpassword-salt-keylen-options-callback)

邀请码未配置或不可验证时关闭注册，不能沿旧代码“空邀请码即任意注册”。注册尚无accountId，使用接口主合同的独立注册作用域（worldId、规范loginName、requestId），成功注册的账号、凭据、非秘密请求摘要和邀请授权事实同次提交；重查必须验证原账号口令与已记录的原邀请授权，不能向未认证者回账号结果。密码/邀请码明文不进入payloadHash或回执。长度、Unicode/登录名规范化与失败显示只读主数据/接口合同，本节不另定第二套字段校验。

账号持久版本为account.revision，创建时为1，对外名为accountRevision；真实角色链接或持久成功登录事实改变时，每个事务递增1，重复原注册/选角结果和只签发内存会话不递增。authRevision独立用于凭据更换/会话撤销，不能拿它替代账号乐观并发版本。注册/login校验精确同源Origin和application/json，不要求尚不存在的会话CSRF；其他已登录写请求同时校验会话CSRF。

M5若启用v1凭据导入，只保留验证旧密码所需字段并标legacy；第一次成功登录后用新随机salt升级到上述scrypt，凭据和authRevision改变先提交再建立会话。不需要也不能恢复旧明文密码，M0不为此保留旧SHA-256新注册路径。

重置或换密码递增authRevision并撤会话。M0会话状态唯一采用内存表：账号cookie最长7天、角色会话最长24小时，表内绑定账号/authRevision、角色/世界/代际、到期与撤销状态；不持久化token或选择另一种跨重启续会话方案。每次受保护请求核对当前authRevision与绑定，退出立即撤会话，重启全部重登。永久成功登录事实仍按接口合同持久保存，不能因活会话不落盘省掉该事实。密码错误/限流不改变角色资产，账号注册失败不能顺带创建新角色或发出生奖。

## 7. 备份、观察与未来故障验收

M0需具备受控导出一致恢复集合、校验并在独立目录恢复的原语；不要求现在部署异地备份服务。M5采用前再实测的发布建议为每小时一份完整恢复集合、保留最近24小时，另保留14份每日与8份每周备份，至少一份副本离开主机。本轮没有创建定时任务或证明异地复制已经完成。每份必须覆盖快照、连续日志、配置版本、仍被引用的私密随机根、账号凭据/去重/历史/唯一账；上传完成与摘要验证后才标available。备份中不得混入另一saveEpoch的CURRENT。

推荐目标：进程崩溃RPO为0个已成功资源事务；单机磁盘灾难RPO不超过最近一次成功小时备份；小服恢复RTO目标30分钟。后两项依部署与演练成立，目前未测，不作为用户的可用性承诺。

| 故障点 / 未来用例 | 必须观察到的结果 |
|---|---|
| F-ST01 连续两次保存＋重启 | 第二次状态存在；覆盖旧JSON后续写停滞，不沿用历史测试全绿结论 |
| F-ST02 扣费计算完、写日志前崩溃 | 无成功回执/无已到账SSE；重启没有半笔扣款，原request可查/安全处理 |
| F-ST03 完整持久帧后、HTTP回执前崩溃 | 重启已提交同结果；原requestId不再扣发 |
| F-ST04 日志末尾短写/中段损坏 | 仅可证明的半写末尾可截；中段损坏停止写入，不自动造新世界 |
| F-ST05 写新快照/换CURRENT任一点崩溃 | 旧或新完整恢复集合之一有效；没有缺日志的混合态 |
| F-ST06 卖家离线/两个买家/关闭进程 | 钱、税、同uid、listing和两人回执一致，仅一笔成交 |
| F-ST07 同request不同payload/30天后重放 | 冲突或已有终态摘要，不能当过期新请求 |
| F-ST08 日周授予、古墓旧周结算同时重启 | 初始化/补期一次，旧run只扣旧周帽，票不被晚领移周 |
| F-ST09 outbox发出后未标送达就崩溃 | 可重发同eventId；十声/出师公告不生成第二条业务历史 |
| F-ST10 缺旧配置/未知uid/双正本 | 原数据隔离、相关写功能阻断；不降级成0/白装、不抽新唯一 |
| F-ST11 v1/内测/正式重置 | 按矩阵核账号/资产/历史，不继承测试首个、不开第二正本 |
| F-ST12 备份恢复演练 | 从实际备份独立启动、核摘要与业务不变量，记录真实RPO/RTO |

观察指标至少包含写者状态、最后成功commitSeq/时间、提交失败/未知结果、待投outbox最老年龄、最后可恢复备份切点、业务键冲突、负余额/多位置uid、在途旧period和未知配置隔离数。应用/诊断日志只记必要ID/错误，不记录Cookie、密码、凭据摘要或私信全文；私密journal按第6节保护，不能直接作为可分享诊断包。验收时以真实执行报告逐条关闭；本轮只完成方案与静态检查。

M0先验证单根单写者、初始化与创角一次、连续两写、同键重查、持久提交前后中断、快照切点、遗留锁受控恢复、损坏拒绝及旧代际写入拒绝；使用当期已启用的基础资源操作，不为此提前实现市场、古墓、师徒或十声。F-ST06/08/09/10中涉及后期对象的子场景随M2～M4启用后补验；30天压缩/日志回收、完整正式迁移/清档、异地备份与RPO/RTO联验在M5完成。后期部分尚未实现不妨碍M0开工，也不能提前写为故障矩阵全通过。
