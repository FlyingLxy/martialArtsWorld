## 1. 公共身份、可信时刻与提交顺序

| 字段 / 量 | 本合同的唯一职责 |
|---|---|
| `worldId`、`saveEpoch` | 世界与存档世代；恢复同一日志不增加epoch，合法换档才增加。旧epoch的连接/命令不能续入新账 |
| `accountId`、`characterId` | 已鉴权账号与角色；不另造roleId，不以名字、SSE连接或浏览器页标识角色 |
| `revision`、`controlRevision`、`commitId` | revision为聚合持久状态版本，角色controlRevision为可操作状态版本；纯泡点未升级只改前者，升级/任务达成/资格到期等同时改两者。wire的stateRevision=revision、committedRevision=controlRevision，eventSeq与commitId另有含义，不能混用 |
| `serverTime` | 进入串行结算段时捕获的服务端UTC毫秒时刻，整个事务只用这一份；客户端时钟不能回填 |
| `committedAt` | 日志耐久完成时间，只说明何时可确认，不替代已确定的事件/奖励归属时刻 |
| `world.worldRuntime.dayNightEpochAt` | 固定世界昼夜纪元，本轮沿旧绝对时间取模选`0`（1970-01-01T00:00:00Z），准备态/active均保持0，不取进程启动或首次激活时刻；activatedAt另记真实启用时间 |
| `recoveryWatermarks.lastCommittedServerTime` | 最近耐久事务的逻辑时刻，用于拒绝倒退与重复处理；不是离线XP锚点 |
| `processBootId`、单调计时锚点 | 只属进程内调度；重启换bootId，不能把旧单调计时读数带入新进程 |

同一进程用服务端UTC锚点与单调计时计算等待和有效秒；实际日/周/小时归属仍按服务端UTC转换为Asia/Shanghai。时刻不允许倒退：检测到系统时钟回拨时，逻辑时刻至少保持最后已提交值，周期游标不能倒扣/再授。若启动时钟早于最后耐久时刻，标记`clockState=needs_check`，只允许鉴权、聊天和只读恢复，暂停依赖截止/产出的写入，待服务端时钟恢复可信后从原游标继续；不能用清空游标“修钟”。M0运行中UTC低于上一观察值，或abs(ΔUTC−Δ单调毫秒)>2000，即进入needs_check并停止时间写；2000ms是检测阈值，不产生额外在线额度。启动UTC低于耐久高水位同样拒绝时间写，跨进程不比较旧单调读数；受控校时/核对后才重建锚点。向前跳钟不得拿跳过时长补在线产出；未来部署验收须覆盖错误时钟，不在本轮假称已处理过真实NTP事故。

永久银两使用总模型的`silverMinor`整数字符串（分），未满分收入另存`silverRemainder`精确有理对象（numerator/denominator整数字符串、0≤n<d、约分，零0/1）；连续XP使用§2.3的18位值加有符号精确有理尾差，HP/MP纯上限变化依属性合同的比例锚点。UTC时间是毫秒整数，不用浮点字符串作日期比较；经济参数的最终取整规则不因恢复重跑一遍。

每个时间事件遵循：**读最后已提交状态 → 分段计算/校验 → 以稳定业务键形成变更 → journal耐久提交 → 更新已提交内存投影 → 回执/outbox**。每2秒泡点也先持久化后展示；不能把已展示收入留在仅内存快照里。单进程、单写者的JSON snapshot+journal是本轮持久化方案；恢复读snapshot后按commitId重放后续已提交日志，半截记录不当成功，不另开一套时钟存档。

玩家新命令采用独立耐久 **prelude（前置时间结算）**，顺序固定如下：

1. 先校验认证、纪元、格式、大小/限流和命令白名单，查询原幂等键。原成功/拒绝回执或永久摘要直接返回；同键异payload冲突。此步骤在prelude之前，同请求重试不是新的结算或操作。
2. 进入单写者后再次查同键，捕获本次权威serverTime；在同一串行处理位置内，先按旧状态结至该时刻，处理到期/日周与升级等结构边界。若有持久变化，以独立prelude事务提交，使用时间段/周期/授点业务键，不预占客户端命令的requestId。无变化不虚造提交。
3. 只在prelude耐久后比较新命令的`expectedRevision`与最新`controlRevision`，以及所需对象版本。若prelude升级或到期使版本改变，返回未受理的版本冲突；**该拒绝不回滚已经入账的时间收益**。拒绝命令本身没有扣发，不能把它解释成钱包自上次快照以来从未变化。
4. 校验通过才进入该命令自己的草稿/耐久事务；prelude写失败或提交状态未知时，不继续执行命令。纯未升级XP/银两积分只推进stateRevision，真实结构变化才推进controlRevision。合法no-op或业务拒绝只保存回执，不提高未变化聚合的revision/controlRevision。

外部定时器使用同一时间结算原语，不与prelude重复消费区间。两次独立提交各有自己的commitId，命令回执不能将prelude伪称为同一资源事务；恢复时保留已经提交的prelude，不用失败命令去补偿撤销。

## 2. 在线lease、多连接与10秒补算

### 2.1 连接是证据，角色只有一条时间线

`GET /api/v1/events`用已鉴权fetch SSE建立连接，`connected`控制帧给`connectionId`。独立 `POST /api/v1/presence/heartbeat` 每5秒ACK一次，body为`protocolVersion/connectionId/saveEpoch`，身份读取HttpOnly账号cookie与`X-Character-Session`；响应含serverTime与leaseExpiresAt，具体结构只读命令表。

| 运行态字段 | 规则 |
|---|---|
| `presence.connections[connectionId]` | 绑定worldId/saveEpoch/accountId/characterId，记录`lastAckAt`、`leaseExpiresAt=lastAckAt+10000ms` |
| `presence.effectiveIntervals` | 同角色所有有效连接lease的时间并集；不得按连接各结一份收益/人数 |
| `presence.online` | 此刻至少一个合法连接lease仍有效，且流未被明确关闭；heartbeat不能为不存在/已撤销的流新造lease |
| `idle.intentEnabled` | 角色是否主动选择修行；断线不等于手动取消意图，但无有效在线区间就不产出 |
| `idle.effective` | intent、在线、合法scene/location/档位、非战斗/非私宅/非古墓等条件同时成立 |

SSE明确关闭立即撤该lease；另一个有效连接仍在则角色不离线。静默断网最迟到剩余10秒lease结束才被识别，这是**协议能观察的在线边界**，不声称精确知道用户物理断网的瞬间。未ACK不续lease，服务端向客户端发送SSE不能自己充当客户端ACK。heartbeat是非持久连接端点，不写资源requestId/角色revision；真正时间收益仍进入持久事务。

重启不恢复旧connectionId或lease。重新鉴权后创建新lease，再判断是否可恢复原修行意图；旧在线区间、旧heartbeat、历史SSE重放不构成新的在线依据。`streamId=(worldId,saveEpoch,characterId,projectionVersion)`是稳定投影流，与临时connectionId分开，不因登录新造第二条角色收益线。

### 2.2 补的是已知在线延迟，不是离线收益

角色保存`idle.lastSettledAt`、`idle.lastCommitId`、当前scene/location/tier、参数版本、经验/银两余数及六修行状态。每次timer或会改变收入条件的命令，先计算从lastSettledAt到serverTime的**已知有效在线区间**。

- 一次延迟补算最多10000ms，保留从lastSettledAt起最早的合格区间；超出部分记`droppedCatchupMs`，不发XP、银两、原矿或值守进度，随后将锚点推进到serverTime，不能下次继续领被丢弃段。
- lease已经结束后的部分、主动停止、战斗、私宅/古墓及非法地点均为0。存在暂停事件就按事件切段，不能拿恢复后的合法状态回算整个间隔。
- 10秒帽不是每次重连奖励，也不允许客户端提交“上次在线时间”。进程重启时清空在线证据，停服区间一律不补在线XP/银两/摸矿/日常或周常修行秒。
- 聊天、读案卷和查看行囊不暂停修行。改派/切场景/档位/人数/时段/升级/进入战斗等边界，先结算旧区间，再切新状态。
- 最多丢尚未提交的尾段；已durable且尚未到达客户端的两秒收益由SSE补发或查询返回，不能重新发一次资源。

积分内部跨级临界可为非整数毫秒，以主合同的有理偏移记录并按锁定XP速率求段；对外serverTime与日/周边界仍为整数毫秒。不要先把升级偏移舍到整毫秒后再算新等级H，也不要把银分精确化误称XP理论公式无限精确。

例如L1、C=1、M=1、无衰减，2秒应得`1000/1800`XP和`0.25×600×2/3600=1/12`两。首次结算记XP高精度余数、银两8分及精确1/3分尾数，连续12个有效两秒段总得1两；断线重连不把每段都重新向上取整。timer延迟12秒且全段在线，只结最早10秒，记丢弃2秒并推进锚点12秒；下次不再补那2秒。

### 2.3 连续XP的可持久化精确尾差

M0固定公式工作精度50位/HALF_EVEN；`need(L)`用该mathVersion计算原曲线后一次落18位并锁入配置，运行中不能用宿主`Math.pow`重新得到另一阈值。连续经验对**已锁定速率**采用精确有理积分，字段如下：

| 字段 | 单位、范围与唯一含义 |
|---|---|
| `xp` | 非负、固定18位的本级XP十进制投影 |
| `xpRemainder` | `{numerator,denominator}`，有符号整数串/正整数串，单位XP；约分、零0/1；范围为`−1/(2×10^18)≤n/d≤1/(2×10^18)` |
| `idle.xpRatePerHour`及规则引用 | 每小时XP的规范非指数十进制串；在真实等级/场景/条件变化处按50位规则锁定，保存math/economy版本及其输入状态引用。存档、读界面、2秒timer或重连不重新选择速率 |
| `idle.lastSettledAt`及已结时间事实 | 服务端UTC毫秒和已经消费的有效区间；与银分/其他已启用消费者同一prelude提交，不为XP另结第二条时间线 |

权威本级经验只有一个组合值 `X=xp+xpRemainder`。对L<60校验 `0≤X<need(L)`；投影xp可能因向上舍入恰好等于need而实际X略小，此时不能提前升级。规范表示为 `q=roundHalfEven(X×10^18)`（用BigInt有理数作精确整数取整），`xp=q/10^18`，尾差=`X−q/10^18`；恰半时q为偶数。规范化只改变表示，不丢弃任何X。初始xp为`0.000000000000000000`、尾差0/1。

把锁定的有限十进制小时速率转成有理数R。一个有效片段d毫秒（内部可为有理数）产生 `ΔX=R×d/3600000`，加到完整X后重新规范化。遇升级时先计算 `τ=(need(L)−X)×3600000/R`；若R>0且τ不大于剩余有效段，则旧等级XP与H只结到τ，精确扣need、升一级/授点/初始化，再锁新R/H继续剩余段。R=0的合法状态无升级分支，但其合法银两等消费者仍按自身规则结算。绝对端点与period边界保持整数毫秒；内部τ不得先舍到整数毫秒，也不把接口已展示的xp当作下一段X。

真实换速率、暂停和跨period时，先完成旧段，再保留原XP尾差切换R；跨period本身不清本级XP。离散奖励先按该奖励规则一次计算最终18位`awardXP`并保存原奖励账，将这个有限小数精确加到X；不重算已发奖励，不把旧尾差再次当奖励发放。一次离散奖若跨数级，逐级扣同版本need并只发一次对应等级权益。

抵达60级时固定xp=0、尾差0/1，丢弃该次尚未用的XP；剩余合法在线区间仍按L60的H结银两，后续实际XP授予为0，不折现、不继续建need(60)升级机会。重启恢复同一X/速率/已结时间事实，清掉旧在线证据，不能按停服间隔补XP。

确定性验算：L1、R=1000时2秒X=`5/9`。`12×2秒`、`3×8秒`和一个合法24秒区间在**没有触发10秒延迟丢弃帽**的积分原语对照中均得X=`20/3`，规范xp=`6.666666666666666667`、尾差=`−1/(3×10^18)`，银两100分/尾数0。生产timer一次延迟24秒仍按§2.2只补10秒，不能用这个数学等价例绕过延迟帽。若把每跳5/9单独round18后直接相加而不留尾差，会错误得到`6.666666666666666672`。

## 3. 三类日历桶与世界昼夜

所有桶用左闭右开区间；恰到边界属于新桶。持久记录桶的起点UTC毫秒与可读ID，不能用客户端当地日期猜桶。

| 周期字段 | 定义 / 示例 |
|---|---|
| `dayId` | Asia/Shanghai当地日期减5小时后取日期；例2026-09-14 04:59属`2026-09-13`，05:00属`2026-09-14` |
| `weekId` | 当前时刻所在的“周一05:00至下一周一05:00”之起始当地日期；上述04:59属`2026-09-07`，05:00属`2026-09-14` |
| `hourId` | Asia/Shanghai自然整点小时；例`2026-09-14T05+08:00`，与05:00日界分开 |
| `worldCycleId` | `floor((serverTime−dayNightEpochAt)/7200000)`，全服同120分钟；不能按角色上线、首次激活或重启重排 |
| `worldPhase` | 本轮内0～20分卯、20～60分午、60～80分酉、80～120分子；阶段只读固定纪元 |

每个新命令按§1先完成独立prelude，再校验其最新预期版本并执行；原回执重放不触发这条新命令路径。prelude内先结清边界前应算的旧在线区间，再处理周期游标与已到期状态。跨05:00的一个2秒tick要切两段；跨等级使用§2.3的精确X和有理临界点，扣need后再用新E/H与门槛算剩余有效秒，不能全段套结算后的等级。

持续在线原矿的3600秒阈值若恰在旧日最后区间完成，先按**贡献该区间的sourceDayId**记旧日原矿，再清新日累计；不是把旧日3598秒带到新日接着攒。由目标达成生成的任务事件则用其实际达成时刻求completionDayId/weekId，恰05:00归新期。事件时刻、来源桶与耐久完成时刻是不同字段，不能互相覆盖。

世界战斗XP/银两/普通材料小时额度归**最终胜利结算serverTime的hourId**，按当时角色等级将实发值除E/H记归一份额，升级不清额度。世界银两裁帽后floor到分，来源账只读本次实际授予量，保留钱包既有修行尾数、不把它的进位归因世界来源。首领/稀有另锁开战cycle/window；古墓另锁entryWeekId，不能把这些语义都塞进一个`lastReset`。

## 4. 初始化、lazy补期与不攒存的帽

### 4.1 资格库存不是完成奖励

每个资格池保存`initializedAt`、`initializationCommitId`、`lastGrantedPeriodId`、`available/reserved/ready`及各资格的原始period。初始化与本期授予同一事务去重；先确定第一次达到门槛的事件时刻，再初始化该期。未达到门槛不预攒。以下只复写第4项已定推荐起点：

| 池 / 字段 | 初始化 | 此后授予 / 总容量 |
|---|---|---|
| `dailyStock` | 创角本日5份 | 日+5 / 15；预留和完成待领也计容量 |
| `energy` | 创角本日100 | 日+100 / 300；开战扣一次，败逃不返 |
| `weeklyOreStock` | 角色首次40级，本周1份 | 周+1 / 2；每份完成给陨铁3 |
| `weeklyCraftStock` | 角色首次50级，本周1份 | 周+1 / 2；每份完成给神兵碎片4 |
| `worldBlueQuota` | 创角本周12 | 周+12 / 24 |
| `worldPurpleQuota` | 角色首次20级，本周2 | 周+2 / 4 |
| `worldOrangeQuota` | 角色首次40级，本周1 | 周+1 / 2 |
| `worldYinQuota` | 角色首次20级，本周2 | 周+2 / 4 |
| `dungeonAttempts` | 角色首次20级开放古墓，本周4 | 周+4 / 8，三难度共享 |

首次达到等级的初始化跟升级事件同commit，不依赖玩家打开哪家公告或挑战哪个怪。世界紫/橙/阴晶还需各自的怪等级、有效级差、合法目标池等条件，初始化不是立即发图纸/材料。三条世界保底`pityProgress`初始0，实际成功发对应奖才清0；跨日/周、停刷、资格耗尽不清，0精力有效步长0.30按固定精度保存。

lazy补期在登录、相关命令或后台维护时执行，逻辑效果一致：若已跨n个未登记周期，按n×每期授予补到容量上限，**同时推进lastGrantedPeriodId到当前期，即使容量满而新增0**。跳过的超帽授予不形成待领债；不需离线运行一场游戏或伪造每日登录。共享日常的单份资格保留原期与稳定序号，公共/门派改入口不增份；第一次接取锁L/E/H/版本，后续取消/换题/晚领不提高。

补期业务键用`(worldId,saveEpoch,characterId,poolId,targetPeriodId)`；读取同一键的重复结果不再授予。初始化与同一期补期必须共享已授期事实，不能创角先给5、随后refresh又给5。不可把当前未满15解释成重新补齐15。

### 4.2 有效使用计数到期归零，不补物

`dailyUsage[dayId]`包括购种8/播种8/收获12/实际食用8、公共摸矿6和家园矿坑1；`weeklyUsage[weekId]`包括摸金令兑换4；`hourUsage[hourId]`包括世界XP0.5E、银两1.5H、普通材料参考价0.5H。它们初值0，进新期记新桶，离线缺了几期也只得到当前期0使用量，不赠菜/矿/材料/银两。

公共摸矿另存`rawOreProgress={dayId,effectiveMs,granted}`；仅合法有效在线秒推进，每3600000ms给1，日帽6，满矿袋时按原经济合同记已处理额度而不补发。05:00清本日未满阈值进度，家园坑不代领过去天数。生产计时独立于此在线时钟：人在公共点修行同时炉在离线加工，仍按公共修行条件计秒；“生产等待不计”只表示光等待订单不会自己产生在线修行依据。

古墓材料使用`dungeonMaterialUsage[entryWeekId]`，阴晶20/古金丝4/镇墓泥1；保留仍有在途run的旧周桶直到结清，不因为跨周就删。世界阴晶资格与古墓来源帽分开，最终物品同ID/同绑定。已花掉物品不释放产出帽，超帽不顺延或转现。

## 5. 目标达成、领奖与周票的两个时刻

| 耐久事件 | 固定字段 | 下游读取 |
|---|---|---|
| `TaskObjectiveSatisfied` | qualificationId、completedAt、completedLevel、completionDayId、completionWeekId；同资格一次 | 达成时≥40的合法共享日常，每周5份形成`bonus.daily.mojin_weekly`票1资格 |
| `TaskRewardCommitted` | qualificationId、rewardGrantedAt、awardWeekId、锁定奖励档与一次领取键 | 发日常XP/银两并消耗原stock；事件之前已存在有效WQ资格时，推进各类最老未满资格 |

目标完成未领奖也可挣周票；不能等升级/跨周后将completedAt/Level改为领奖值。目标已完成不可通过放弃/重置ready再次发目标达成事件；若界面允许取消展示，仍保留该资格完成事实和去重键。周委托读成功领奖事件，不在目标达成和领奖两个时刻各推进一次。

日常值守另保存该qualificationId的`guardEffectiveMs`：在本题公共安全入口累计360000ms完成1份，按最早预留未完成份逐段分配；一段秒数不复制给同批多份日常。满6分钟的精确阈值形成一次目标完成事件，阈值后的新时间才可进入下一份。换到不合格位置、断线或战斗暂停，跨日保留已记秒；尚未接取的历史修行不倒填。

两类WQ各自保存资格的`workUnits/idleEffectiveMs/normalVictoryCount/consumedSourceEventIds`。公共安全修行每1080000ms给1单位、合格普通胜利每6次给1单位，日常成功领奖或独立核查每次给1单位，合计10单位完成；目标池与等级差读取日常表，不扩大为所有风险点或教学战。每类只推进最老未满资格，未有资格时不存未来可兑换进度；同一有效秒可以同时推进一份DQ与陨铁/碎片各一份WQ，但不复制基础修行XP/银两。某份WQ满10后不把**同一个**已消费事件再给下一份，只有之后的新事件/新区间才可推进；未满单位的合法余秒/计数随原资格跨日周保存。

票资格保存`earnedWeekId/earnedAt/expiresAt/state(pending|claimed|expired)`，有效至下一周结束（原周开始+14天）。最多本周/上周两期各1，满实物票袋8不阻断日常基础奖，也不覆盖老期；跨到截止时刻先标过期，再处理领取。阴晶兑票前先处理仍有效的待领，持有仍满则不扣阴晶；10秒lease、dailyStock15和票袋8不互相借容量。

**跨周手算**：2026-09-14周一04:59，角色40级完成本周第5份日常目标，记录completionWeekId=`2026-09-07`，形成旧周票资格，有效至2026-09-21 05:00。05:01才领日常：消耗原资格、按首次接取锁定档发奖；TaskRewardCommitted的awardWeekId=`2026-09-14`，可推进该事件前已有的新/积存WQ资格，票不挪新周。若目标达成时39级、领奖时40级，仍不追发这份的票进度。

## 6. 六修行、风险与现实期限

角色持久化修行种类、intent、scene/location/tier、`continuousEffectiveMs`、`runeRemainingEffectiveMs`、`lastEligibleBattleSettledAt`、日月当前/已排定取向与生效cycleId；每次结算必须知道参数版本。其余A/M按已提交外部状态重算，不让客户端直接提交满足度。

| 模式 / 状态 | 断线 | 重启 / 时间推进 | 主动变化 |
|---|---|---|---|
| 吐纳 | 连续有效秒暂停，同场重连保留 | 停服不加秒 | 主动停修、换场/开战归零；同场已提交进度不被读界面清空 |
| 符文 | 剩余有效秒暂停 | 停服不消耗支持秒，不重新收布设料 | 换scene解除、不退料；同scene风险收功只暂停；布设原子炭1+最大MP10%，7200有效秒，不叠容量 |
| 骑士誓约 | 该角色不再计同伴；其他角色从lease变化时刻切段 | 重新鉴权后按真实有效同伴重算 | 只同门/结拜合格身份，重叠计1，不造NPC同伴 |
| 忍宗收束 | 同场真实在线人数按lease并集变更 | 重启无旧连接人数，恢复后逐次切段 | 仍按人数，不能改读昼夜或独占席位 |
| 战意 | 实际7200秒窗口照常过期 | 用lastEligibleBattleSettledAt与当前serverTime比较，不延长剩余窗 | 仅合法公共世界胜利/非空奖励资格且角色不高于怪超10级；不看随机中材，零奖/败逃/教学/对练不刷新 |
| 太阳日月 | 全服时间继续，不能保存有利时段 | 按固定epoch读当前phase；不从卯时重开 | 下一完整cycle才生效的新取向只一次，离线跨界也按预定cycle生效 |

战意和重伤是绝对期限，符文与吐纳是有效秒；不能用统一“lastSeen差值”同时推进它们。若风险保护或权限变化实际迁出scene，按换场规则清吐纳/本地符文；仅同scene收功不搬走符文。纯界面重连不再扣原布设资源。

### 独占练功席位的120分钟硬截止

既有内室、闭关处与剑冢独占练功段按scene登记`sceneLease={leaseId,characterId,acquiredAt,expiresAt,returnSceneId,returnLocationId,status,revision}`，保存于worldRuntime的sceneLeases；每处最多1条active，角色同时最多占1处。`expiresAt=acquiredAt+7200000`按现实服务端时钟固定，与120分钟世界昼夜cycle无关。剑冢公开见证区没有此占位条件，不为公开交互另造scene/location ID。

已鉴权角色主动申请且门槛/空位合法时，占位、当前位置与起止时刻同一耐久提交。重试同一次申请返回原lease，不延长expiresAt；某个连接重连而另一个有效lease仍在时继续原独占期限。最后有效presence lease消失、主动离开或到期时，先结到该边界应算的有效修行，随即释放独占位并把角色记到场景表已有安全返回点；重启同样释放并安全返回，不保留离线占位。若边界发生在已合法开战期间，释放席位并记录战后安全落点，原battle仍按§7完成，不能借席位到期或拔线取消战斗后果。

重新上线不恢复已释放席位；未来新的主动申请须重新验空位，服务端既不自动续租也不优先原持有人。并发合法申请按单写者受理顺序决定一人成功，其余明确返回无位；没有已受理席位的请求不会被默默放入长期排队。**这只保证单席、硬截止和断线不占位，不证明长期使用公平。** 本轮不新增每周期额度、重入冷却或预约队列；第6项验证无位提示与重新竞争体验，需要这些机制时再单列建议。

## 7. 世界战斗、切磋与服务器崩溃

### 7.1 持久化的是一场战斗聚合

| 字段 | 解释 |
|---|---|
| `battleId`、`revision` | 世界内同一战斗聚合；双方角色只保存引用，不各自克隆一份战斗 |
| `participantCharacterIds`、开战快照 | 同world/saveEpoch，保存合法装备/技能/HP/MP与精力档、目标/掉落挑战；跨角色结算一起锁 |
| `phase`、round/行动顺序、`opportunityId`、`actionId` | 当前合法机会与服务器预发一次行动槽；玩家、超时、托管竞争同一槽 |
| `checkpointRevision`、`checkpointCommitId` | 最近完整耐久行动的状态；与HP/MP/物品/冷却/每场次数/随机step同commit |
| `rngState`、`rngStep`、`rulesVersion` | 可复现随机与规则版本；命中、先手、控制、掉落不能因恢复另抽 |
| `waitKind`、`inputWindowMs`、`remainingWaitMs`、`waitRecordedAt`、`deadlineAt` | 手动输入机会首次预算10000ms；最近checkpoint记录剩余预算与记录时刻，同进程deadlineAt=waitRecordedAt+remainingWaitMs，恢复后从该剩余值重排；不追赶停服积压回合 |
| `autoPolicySnapshot`、`autoPolicyVersion` | 开战锁定的合法托管策略，恢复不用客户端新塞的最优策略 |
| `entryWorldCycleId` / `entryWindowId` | 首领/稀有开战合法窗口；胜利奖励的小时桶另按实际结算时刻 |

每个主动行动含支付、全部反应/致死保护、状态及机会推进作为完整结算单元；若该行动后战斗结束，奖励、配额、结算标记同commit。回合末也需耐久checkpoint，不能已播放DOT死亡却没记录消耗或结局。每行动去重和随机步细节读资源合同，时间触发键由battleId/actionId派生，不用connectionId。

### 7.2 断线不替玩家逃跑

世界PvE与双方同意的切磋在任一/全部参与者断线后仍由服务器按锁定策略进行。需要输入且截止未收到合法选择时，使用已有普通拳脚；无合法目标或已失去行动资格才跳过，仍按既有回合时序推进。不得自动逃跑、暂停对手或冻结不利状态；不因断网免掉实际战败后果。禁止离线自动开下一场世界战斗。

玩家命令与超时动作争同actionId；谁先耐久提交谁占该槽，另一请求返回现有结果/过期，不执行第二招。控制跳过按原规则仍推进机会；本合同不改变技能CD、护体回合数、先后手或伤害。未选入的非切磋PvP/多人模式继续关闭；如以后启用，也必须恢复同一世界battle，不能靠拔线逃罚。

本轮明确推荐手动`inputWindowMs=10000`，只规定一次输入机会的等待上限，不用它另定回合速度或动画时长。输入槽耐久开启后发布deadlineAt；同进程按单调计时等待，串行受理时serverTime≥deadlineAt的选择不得抢过已到期的托管动作。客户端倒计时、重复connected和SSE重放不续期；deadlineAt是显示与受理边界，不是客户端可更改字段。

服务器崩溃不同于客户端断线：先从snapshot+journal恢复所有battle的最后已提交checkpoint，停服期间不补任何战斗回合。`remainingWaitMs`以最后耐久记录为准，不猜测断电前尚未确认的等待；启动完成后以恢复时刻加该预算重排一次下一行动，先耐久记录新的waitRecordedAt/deadlineAt再发布，原opportunityId/actionId不变。预算0只触发当前待决槽一次，不能看到旧绝对deadline在过去就连跑几十次积压普攻。两名玩家即使分别重连，也只订阅同一battleId；一人尚未登录不妨碍已恢复世界战斗继续托管。

## 8. 古墓冻结、家园计时与一次恢复

### 8.1 古墓按最新checkpoint续局

`dungeonRun={runId,entryWeekId,difficulty,status,phase,seed,rngStep,floor,nodeId,battleId,checkpointRevision,frozenAt,freezeExpiresAt,foodLocks,materialLedger,settlementCommitId}`；status有限为`running/frozen/settling/settled`，phase另记录准备/节点/战斗中的具体位置。`dungeon.enter`同一耐久事务创建run、扣挑战/票、锁seed并给初始冥钱，实际5选2只在此后展示；`dungeon.prepare`随后一次提交真实已选奇物和食物准备锁，不能要求尚未展示候选时就提交选择。

- 本人最后一个有效lease失效时，在单写者顺序中冻结run。若一个行动已在提交，先提交该完整行动再冻结；尚未占槽的后续动作拒绝执行。记录冻结时刻与`freezeExpiresAt=frozenAt+86400000`。
- 24小时内由本人明确恢复同run，校验epoch、未结算与权限后继续最新checkpoint；不从“本场开始”重置HP/MP、CD、已用食物、奇物或随机。查询、heartbeat和SSE补发不算恢复，不顺延截止。
- 若serverTime≥freezeExpiresAt，先进入settling按失败规则结算，再返回已结束；不能晚到一毫秒仍恢复。真正恢复running后清本次冻结状态，下次断线再建立一次冻结区间；不得仅重复调用查询延命。
- running古墓遇服务器崩溃，恢复时用最后已提交checkpoint时刻作为最晚可靠的暂停起点；停服不补战斗回合。已有frozenAt原样保留，不因重启更新截止。若到恢复时已超过24小时，按一次失败流程；这一绝对超时方案仍需停服保障评审，不声称已经验证可用性。
- 食物锁只预约份数，实际用掉已在对应action commit扣永久库存/日帽。失败不退已用，未用锁在最终settlement一次释放；重放检查锁的commit状态，不把所有入袋份数再扣一次。
- 节点图、选择、未知事件、商店库存、奇物已见/已持池、池空补偿和掉落候选随run固定；重连不补货、不重抽，不新建第9奇物。冻结期间不启动新run或世界战斗。

古墓失败结算按entryWeekId的旧周帽；例如周日入局、周一结算仍裁旧周20/4/1，不借新周额度。次数已于入局扣除，不因跨周/冻结退回；每周新增4仍只补总持有到8，与在途run并存但不能再开第二局。

### 8.2 家园与公共加工不依赖在线等待

作物保存`cropInstanceId/plotId/plantedAt/maturesAt/witherAt/harvestedCommitId`，状态`growing/mature/withered/harvested`。maturesAt由本批已锁配方时长算，witherAt=maturesAt+24小时；离线或重启按当前serverTime读出状态。恰成熟可收，恰枯萎先失效；不会同时收获和枯萎。成熟不自动发成品，已收获食物不再腐坏；播种预留的成品容量随收/枯一次处理。

共享加工保存`jobId/recipeId/startedAt/completesAt/status/claimCommitId`，状态`running/ready/claimed`。公共与家园引用同一个jobId；离线到期仅变ready，不重扣料、不再开新炉，领取一次。当前四公共配方/家园精铁的同队列限制不因重启丢失，未领仍占位。日帽属于实际播/收/使用时相应dayId，不把离线成熟次数当作新增每日播种资格。

## 9. 随机世界窗口与唯一装备90天

普通抽取无跨重启新奖励；精英保存每角色/encounter的`lastDefeatedAt/nextEligibleAt=+1800000`，首次尚无击败记录可挑战，失败不伪造击败时间。稀有按world/encounter保存`activatedAt/windowId/windowStartAt/windowEndsAt/scheduleSeed/scheduleStep/nextWindowAt`：窗口300秒，前窗结束后均匀抽3600～14400秒等待；首次启用把已持久化activatedAt当作前窗结束基准，抽第一份等待一次，不能每位角色上线另抽。抽样一旦提交不得重启重抽。停服越过的窗口只记过去，不补怪/广播/奖励；后续窗口从同一持久随机序列推进，不能以“现在+重新抽”改分布。若后台分批追时，入口先显示恢复中直到得出当前窗口，不能临时默认开放。首次窗口的activatedAt基准是本轮初始化补齐提案，不增加刷新频率或稀有实例。

首领轮次读取worldCycleId，持久化每角色/encounter已领奖轮次与在途占用。跨窗口已合法开战可完成原battle；窗口关闭只阻止新入场，失败不扣胜利领奖次数但已耗精力/药不返。出窗战斗最终提交仍按实际serverTime记hourId与当前可用世界资格，不挪到旧小时额度。

十声沿既有`uniqueDomainId/ownerAccountId/holderCharacterId/uid`，只保存同一正本。免费意向后下一周一05:00开正式7日窗口，至再下一周一05:00截止；窗口和截止候选锁属于world耐久事件，离线不失格。停服跨截止恢复后只结算该轮一次，不重开同轮报名或取消已决定结果。

90天依据`accountLoginByDomain.lastSuccessfulLoginAt`，是账号在此uniqueDomainId任一角色**成功建立已鉴权角色会话**的耐久登录事件，非heartbeat、SSE历史回放或客户端自报。60/83/89天通知以`uid+ownershipTermId+thresholdDay`去重进outbox；90天时进reclaim_pending、禁新战斗引用，待activeBattleRefs(uid)=0才原子回收。登录发生在截止之前则在同一账号/唯一聚合顺序更新基准并取消本次待回收事件，旧定时器带expectedLoginAt校验，不能按旧90天日期再回收。

恰90天的登录不被回写成“期限前”；先处理已经到期的回收状态，后续返还/申诉按唯一合同，不通过改时钟或重建账号登录事件复制正本。连续90天按90×86400000毫秒，不按跨过90个05:00或90个自然日期。成功回收后重置+0、凭证/归属/outbox同事务；时钟只发起该状态转换，不直接再发武器或赔偿，细节读资源合同。60/83/89天停服错过的提醒在恢复后写当前有效阶段的一条摘要并标记已过阈值，不连发过时提醒，也不重放庆祝横幅。

## 10. F18关系的时间边界

本节金额、次数与衰减起点是第5项为F18补齐的明确推荐，来自[数据模型与接口](数据模型与接口.md)§4；不是第4项已经验证的经济结论，也不开放D05仇人玩法。

一般师徒、指点、请客、带游、参观与昵称邀请按总模型推荐`expiresAt=createdAt+600000`，同一邀请的查询/重试不延长。进入单写者时已到期则先失效，晚到接受不扣资源或追认同意；结拜另用下表24小时。参观被接受后形成独立的单次进入许可，有效600000ms并在实际进入时消费；这是进入许可的有效期，不是把正常只读参观强制限时10分钟。交厚≥80免逐次许可，仍服从宅主全关/黑名单。

交情以总模型的`bondPairId`无向角色对为唯一聚合，保存`sharedIdleMs/lastInteractionAt/decayThroughAt/historicalMaxTier`。同一pair仅取双方**同时在线、同一实际公共scene/location且各自合法有效修行**区间的交集；同地点选择不同g档不改变同场关系。每累计600000ms形成一次+1事务，扣除已结600000ms并保留不足阈值的余秒。任一方停修、换场、进战或最后lease失效就暂停累计；恢复不补缺失区间。两个角色timer、四个SSE连接也只能消费同一对同一段时间一次，不先甲加1再乙加1。每个整600秒正向结算以该阈值实际达成时刻更新lastInteractionAt；单纯同场未满阈值、heartbeat、查询与重试不刷新互动时刻。

衰减另走现实UTC时钟：宽限至`lastInteractionAt+7×86400000`，之后每完整86400000ms减1，所以首减在最后互动后第8天。以`decayThroughAt`记录已处理的完整日数，lazy读取跨n个日段只减尚未处理的n次；到下限也推进游标，不积累以后补扣债。历史最高档0/10/30/80/200的下限分别是0/0/10/30/80。新的真实正向事件先结清此前已到期衰减，再加交情、记录该事件时刻并重设宽限；当前权限按当前值读取，不能因曾达知交永久保留其权限。衰减不是Asia/Shanghai的05:00日帽，离线会衰减但不会增加交情。
