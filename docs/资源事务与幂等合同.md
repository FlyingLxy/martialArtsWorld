# 资源事务与幂等合同 v0.1

> 第5项文档提案，2026-09-08。本文把第1～4项的内容与经济规则落实到事务边界，尚未开发或验证。D04绑定、市场、耐久以及十声首发入口等仍按原文的“推荐待审”状态；写出事务并不代替用户批准玩法选择。
>
> 只引用已登记的207个装备模板、45种材料和255条配方/成本事务，不新增产品物品、货币或配方。命令名见[命令与事件接口表](命令与事件接口表.md)，持久化结构与提交协议见[数据模型与接口](数据模型与接口.md)，时钟与恢复见[时钟与断线恢复合同](时钟与断线恢复合同.md)。本文规定“哪些状态必须一起变”，不定义存储驱动API。

> M0直接依赖已按[M0实施基线](M0实施基线.md)采用；原六命令、精确资源表示、独立时间前置事务、初装随机与单写提交进入实现依据。后期消费玩法保持原阶段边界。

## 1. 现有实现与本合同的边界

只读核对的当前实现仍是旧原型，不能把以下能力当成已完成：

| 当前证据 | 第5项需要补齐的边界 |
|---|---|
| `server/http.js:92–96` 调用命令后立即回`ok:1`；`server/state.js:115–123` 标脏后立即SSE | 成功回执、可见资产状态和业务事件只能来自已经持久提交的结果 |
| `store.js:162–178` 合并脏集，在途写存在时返回同一个Promise；`213–224` 原子替换整个JSON快照 | 这是批量保存，不是某条命令的资源事务；不能用“await了一次flush”证明该命令的写集合已经落盘 |
| `server/economy.js:24–41` 先扣款，再`Math.random()`，随后推送 | 花费、随机结果、怜悯计数、实例修订和回执必须同次提交，重试不能另抽 |
| `server/economy.js:199–220` 顺次移除挂单、扣买家、查找卖家并发物；不存在的卖家不会入账 | 买家、卖家、市场托管与税同时成功或同时不发生，不能只有买方完成 |
| 旧装备依赖背包数组位置，旧玩家主键是名字；旧稿曾建议nonce内存保存5分钟 | 新合同用稳定身份与装备uid；请求去重跨重启和压缩保留，不因改名、换连接或超时失效 |

M0存储**采用**单进程、单写者的JSON快照＋追加事务日志；未来MySQL适配必须保持相同语义。旧MySQL批量事务也不等于这里的命令事务。启动时发现无法确认唯一写者、日志完整性或提交状态，应停止受影响的资源写入并按主数据合同恢复，不带着不确定账本继续交易。

## 2. 身份、请求与提交的共同原语

| 字段 | 合同 |
|---|---|
| `accountId` / `characterId` | 稳定私有身份；显示名不是主键。操作者与当前角色取服务端认证会话，客户端指定的角色只作目标声明，必须再校验归属 |
| `worldId` / `saveEpoch` | 逻辑世界与当前存档纪元。旧纪元请求不进入新纪元的资产命令；恢复、清档和跨纪元边界由主数据合同控制 |
| `actorScope` | 由服务端构造，包含世界与认证账号；内部系统事务使用明确的系统域。不能由客户端任意填一个新scope绕过去重 |
| `requestId` | 客户端为一次明确操作生成，重试原样复用；幂等键为`(actorScope, saveEpoch, requestId)`。连接ID、设备ID、当前时间不能替代它 |
| `payloadHash` | 对规范化命令、目标角色/对象、参数、规则版本引用和原`expectedRevision/expectedObjectRevisions`计算。对象字段排序、数值格式与省略字段按接口合同规范化；同键不同hash立即冲突 |
| `expectedRevision` | 角色命令比较`character.controlRevision`；无角色的账号命令比较账号revision。不能用角色每次持久变化都增加的`revision`替代，也不能要求客户端携带整个世界的单一版本 |
| `expectedObjectRevisions` | 对象前置数组`[{kind,id,revision}]`，仅含本命令要求的uid/listing/run/battle等对象；跨角色命令由服务端补齐受影响聚合并重验真实状态。`args.expectedBattleRevision`为battle项的同值显式字段，二者不一致拒绝 |
| `commitId` / `affectedRevisions` | 一次持久提交及其中每个聚合的新revision。一次操作改变多角色/市场/战斗时只有一个提交结果，不允许拆成数个独立成功 |
| 业务唯一键 | 领奖位、资格、装备修订、行动机会、生产订单、古墓局次或唯一迁移自身的唯一约束；即使换requestId，也不能再执行同一已消费的业务机会 |

服务端不接收客户端声明的实际金额、税额、成功率、随机值、掉落结果、剩余次数或完成时间作为权威输入。购买输入是商品ID和数量，打造输入是uid和目标动作，任务输入是已发布选项和实例；实际成本、兼容、产物与结算时刻由服务端从版本化规则计算。报价预览只供确认，不能直接修改资产；影响费用/绑定的规则版本变化须重新预览，不能静默按更贵的新价扣款。

`character.revision`在任意持久状态变化时增加；`controlRevision`仅在玩家命令产生真实控制变化或影响可操作资格的结构变化时增加。纯XP/银两泡点且未升级只改revision；升级、自动进战/胜负、任务目标达成、资格到期也改controlRevision。请求比较control，回执`committedRevision`返回control，并附`stateRevision=revision`；相关对象返回自身revision。这样2秒泡点不让全部命令持续冲突，单写者仍必须用最新余额/物品校验，不能据旧客户端余额盲写。

永久银两使用主合同的`silverMinor`非负十进制整数字符串，单位为0.01两；不足一分的连续收入另存`silverRemainder={numerator,denominator}`精确约分对象（整数串，零0/1），不得先舍入到decimal18；完整算法见主合同§2.3。计数为安全整数；XP、HP、MP、盾和积分的十进制精度与尾数沿主合同。以下人类可读“两”仅为同一余额的显示，不能再存一份可独立改动的`gold`真值。商品/服务最后一次`ceil`到整数两、返料/传承最后一次`floor`沿第4项，不能在重连或每次快照时再次取整。

### 2.1 从接收到成功的边界

1. 验证认证、世界/纪元、格式、大小和速率；确定服务端角色。查询同幂等键：hash不同返回冲突，已有完整回执返回原回执，已有永久摘要返回`already_committed`或原拒绝摘要并要求同步，均不重新执行。这个查询先于revision比较，否则已经成功的重试会被自己提高的revision挡住。
2. 进入单写者后重查原回执；新意图先按M0基线§6独立持久提交时间prelude（无变化不写空帧），再检查最新control/account/对象预期版本。升级等导致冲突则本次意图未受理，已提交的合法时间收入保留。明确业务写集合和唯一键；不能在校验途中先扣第一项材料或发第一件奖励。
3. 在隔离的事务草稿中计算全部扣发、绑定分量、容量预约、随机结果及事件。验证资产守恒与各项上限；无法完成时整笔拒绝，不能落半张订单再“尽量补偿”。
4. 同次持久提交写集合、新revision、业务消费记录、幂等回执、随机/检查点及outbox。提交的耐久判据按主数据合同；在此之前不能发送成功、掉落演出、奖励日志或新余额。
5. 提交成功后发布已提交状态并返回`commitId`、`affectedRevisions`和结果。outbox可以晚发或重复传送，资产不能因通知失败重发。客户端超时只表示不知道结果，不能表示服务器回滚。

仅认证/格式/限流/revision等**未受理**拒绝不占requestId，其commitId为空；进入业务权威校验后的资格不足、余额不足、已绑定等**业务拒绝**持久记录`rejected`终态，并可追到保存该回执的commitId，资源版本不因拒绝虚增。同一键再试仍得到这次拒绝；状态改变后需要新的明确操作和新requestId。合法no-op也记录持久结果。M0保留全部日志/完整回执，不运行压缩GC；M5实现验证后，完整回执30天后才可按主合同压缩成永久摘要，仍保留hash、commitId、结果和对象引用；不得TTL删除后重新执行，存储不足不能临时放开去重。

`UNKNOWN_COMMIT_STATUS`只允许原键重试或查回执；`REVISION_CONFLICT`要求先取新快照，再由用户或已授权的明确新操作提交新键。客户端不能在后台换键“补发”一个可能已成功的购买/打造。幂等解决的是重复执行，不是把互相冲突的不同请求都判为成功。

内部每2秒修行结算不永久生成一条客户端式requestId；以单调`settledThrough`、已结算segment和事件水位防重。该提交产生的一次摸矿、日界资格、任务完成或其他业务奖励仍用独立业务键锁定。恢复日志只安装已提交状态/事件，不能重新运行业务函数或随机数。

payloadHash采用M0基线§6的SHA-256/JCS规范信封，只包含原请求显式内容/报价引用，不混入重试时当前服务端经济版本。初装HMAC的字节输入、域及拒绝采样固定在同基线§5；XP有符号尾差和HP/MP比例锚点分别沿时钟/属性合同，不能用投影值当权威资产。

## 3. 资产、绑定分量与uid守恒

| 不变量 | 必须同时检查的状态 |
|---|---|
| 钱包守恒 | 每笔扣发列清`source`、`sink`或转移对手方；市场银两是买方转给卖方减税，不同时又记系统发奖。所有余额非负，尾数只在合法收入积分中累计 |
| 材料守恒 | 同materialId的总量等于各来源/绑定分量之和；花费从具体分量转到消费流水/托管，退款返回原分量，不凭总数重新推断为可交易 |
| 来源帽与库存分离 | `mat.yin_crystal`只有一个物品ID且均角色绑定；世界与古墓分开计来源帽。花掉库存不释放已消耗的产出帽，购买不挤占免费产出帽 |
| 实例守恒 | 普通装备uid只能处于背包、穿戴、市场托管、安全待领或已销毁中的一个位置。转移保留uid、模板、词条与绑定；只有已登记生成行为才能创建新uid |
| 锁守恒 | 同一uid的修改/转移与`activeBattleRefs(uid)`互斥；市场托管、生产输出待领、传承处理中和唯一保管状态不能被普通背包命令绕过 |
| 投入守恒 | `enhanceLedger`只记真实支付及实际用掉的可追溯抵扣；源账清空、目标份额和来源链同次提交。服务费/铸造成本/未用份额不混进可退打造投入 |
| 容量守恒 | 实物＋已预约输出符合该容器上限，锁定持有是实物中的受限部分而不重复加一次。装备行囊48格（已穿六件不占格）、原矿50、种子32、食物32、票8等使用各自规则，不能拿单笔999件上限代替实际容量 |
| 资格守恒 | 可用、预留、进行中、完成待领都占原资格库存；领取后变已消费。同一资格或领奖子位最多有一次有效发奖流水 |

绑定规则沿[装备材料经济表第8节](装备材料经济表.md)：默认先消费当前角色绑定分量；明确选择“仅可交易材料”时不够即拒绝，不能悄悄补绑定料。输出继承实际投入的最严格归属，并在确认中展示。若出现属于其他角色的绑定分量，当前角色不能消费或混料。来源分量至少能追到原`sourceId/commitId`、binding归属及剩余量；转入托管不会解除这些信息。

装备命令以uid定位，背包位置只是显示索引。穿/卸、打造、重洗、分解、传承、上架和唯一归还都核对当前持有权与实例revision。开战先原子取得所用uid引用并锁定配置；普通战斗进行中不允许改变这些实例。归还/回收进入禁用状态后不能再开新战斗，但不能销毁仍被旧战斗快照引用的正本。

## 4. 角色创建、任务和日周资格

|---|---|---|---|
| 创建角色、`reward.bootstrap.starter` | 认证账号、角色创建资格、故乡合法；服务端分配characterId | 新角色、六件既有L1绑定+0装备、启动奖励记录、当日5份DQ资格及当日刷新水位 | 账号创建操作键＋characterId启动奖励位；重试返回同角色/六个uid，重登/死亡/改故乡不再发 |

| 一次性领奖；例如`reward.ZC-SL-05` | 任务已完成未领；加入门派的当前状态仍合法 | XP/银两、SL身份、`skill.sl.dali_jingang_zhi`、`equip.shaolin.jieyuan_bu_hushou`×1绑定与领奖位同时提交 | 任务奖励位；不能先入门再因背包失败补发整包，合法安全待领也只有同一个uid |
| LY-03/MT-06自选 | 已有里程碑待领、目标模板属于已发布有限池、级别和D03兼容通过；MT-06装备须20级 | 消费独立自选领奖位，生成一个绑定uid；已经发过的主任务XP/银两不再发 | `(characterId,reward.LY-03或reward.MT-06,装备自选子位)`；改选项换requestId也不能两件 |

| DQ/WQ进度与完成 | 原事件合法，资格已存在；相同事实未被分配给同类另一资格 | 按最老未完成资格分配；首次`TaskObjectiveSatisfied`写`completedAt/completedLevel/completionDayId/completionWeekId` | `(qualificationId,源事件ID,进度用途)`；6分钟不能同时填5份DQ，同一事件不能填满同类两周资格 |

| `bonus.daily.mojin_weekly` | 首次目标完成时已40级；同完成周有5份不同合法DQ事实；票奖励位有效 | 挣得该周待领票；领票时检查实物容量8并消费待领位，发`ticket.dungeon.mojin`×1 | `(characterId,bonus.daily.mojin_weekly,completionWeekId)`；票满保留本/上周待领，不阻塞DQ基础奖，过期显式作废不重挣 |

任务“目标完成”和“奖励领取”是两个时间事实。39级达成、40级领奖不补算周票；周一04:59达成、05:01领奖时，票归目标完成的旧周，WQ只按成功领奖事件推进当时已存在的资格。已完成资格不能放弃后恢复成未完成来重刷事件；其完成去重永久保留。教学临时技能、临时装备和借用资源只留在教学实例，任务奖励只解锁该课已登记的一门真实技能。

`quest.claimBatch`只接受本人DQ/WQ的固定子实例列表，最多15项，重复子ID按格式拒绝；按每份资格分别验证、分别提交，返回逐项commitId/status。父请求先持久记录固定列表，重试复用同一子业务键，不把“当前又多出来的资格”加入旧批次；父完成回执的commitId只表示批次状态提交，不代表全部子奖励在一笔事务中发生。已成功子项提高controlRevision不能让同一父批次后续子项误判过期，仍须在单写者内核对每项当前资格与对象版本。一个子项失败不撤销其他已成功子项，也不重发它们。DQ垫款、采购直结与任务检查器物使用任务专用成本账，不进入普通钱包/材料库存供交易、传承或分解。

择承任务还要锁共享领奖位：十派ZC-01的数值奖共“首个旁观”一位；ZC-02/03/04各编号分别跨派共一位；ZC-05仅本派成礼一次。各questId可以分别保留剧情/见闻完成记录，但不能只用各自questId去重而发十遍同一共享XP；撤回求入不清这些共享位，公开试演不生数值奖励。

WQ的`reward.WQ-CRAFT-01`每份只发`mat.divine_fragment`×4，`reward.WQ-ORE-01`只发`mat.meteoric_iron`×3；两周集中领取8/6是两份资格，不是两个入口。实体碎片容量不能设为8而阻止24片兑换核心。具体进度事件条件沿[日常任务与周常委托表](日常任务与周常委托表.md)。

耐久是否首发仍是D04待审。本轮推荐不收费/后置时不得调用修理扣费事务；若批准启用备选，须补齐同样的uid锁、单次实际修理量与费用同commit，不能用接口预留偷偷开始收费。

## 6. 市场跨角色事务

材料托管流通是F16保留目标；普通装备买卖还需D04范围/绑定推荐被采用并开放。对尚未开放的具体标的返回业务拒绝，不能因D04未裁就移除材料流通。市场不开放绕过托管的直接赠送、易货、神兵或十声交易。

| 操作 | 权威校验 | 同一提交的扣发与锁 | 业务唯一键/并发结果 |
|---|---|---|---|
| `market.list` | 角色最多10单；合法未绑uid或具体未绑材料分量；整单P正整数、有限官评V、持有权/无锁、挂牌费足够 | 原物移到唯一listing托管、扣`ceil(0.005P)`、记录P/V/版本/7天期限及原归属 | listingId＋原资产revision；请求重试不重复挂牌；已托管uid不能再穿戴/打造 |
| `market.buy` | 挂单仍active且未到期、非本人、买家余额/容量、卖家稳定账号/角色收款账可达、全部revision有效 | 买家−P；卖家＋P−税；税入sink；托管物转买家；listing变sold；双方回执事件同一commit | `(listingId,terminalSale)`；两买家竞争仅一笔成交，输家不扣钱。客户端不必知道卖家私有revision，由服务端锁写集合 |
| `market.cancel`/到期 | 当前active、操作权限或服务端到期依据；检查同一挂单未成交 | 原物转原卖家或同一安全待领位，listing变cancelled/expired；挂牌费不退 | `(listingId,terminalClose)`；与购买竞争只成功一种终态，满仓不吞物、不生成副本 |

卖家离线不影响到账；卖家缺失、正在删除且无法建立原归属收款账、资产镜像不一致时，拒绝成交并保留托管供恢复，不能扣买家再忽略卖家。角色删除流程必须先收束挂单/待领/生产/唯一保管；不能把名字改成新角色后让新角色收旧款。恢复卖家余额和买方物品时按同一个commit，不分别从较新和较旧的快照拼接。

税公式为`ceil(0.05P + 0.50×max(0,P−3V))`；只从卖方应得款中扣一次。买方只付P。材料在市场转手保持未绑定来源；只有原本合法可交易的分量才能挂牌，不能把部分绑定总余额打包成可交易单。

## 8. 战斗检查点、消耗与终局奖励

| 行动受理 | `opportunityId`、预发`actionId`、`expectedBattleRevision`；合法技能/目标/道具、可用MP/CD/核心资源、当前机会尚未解决 | `(battleId,actionId)`是独立业务唯一键；requestId只负责传输重试。其他连接换requestId不能再打同一行动 |

`checkpointId`只由服务端生成，客户端不能指定回档点。随机状态、行动提交和资源扣发同commit，重启仅恢复最后durable checkpoint；不从开战重算已经喝掉的食物、不补停服积压回合。跨角色切磋只有同一个world内battle聚合，不能两边各重建一场。古墓战斗引用本run与node，不另发普通世界战奖励。

世界离散银两裁帽后floor到分，与小时来源份额同commit，既有连续修行silverRemainder不变。普通所有整分支出只扣silverMinor；世界战败罚金按经济主表floor到分，不能消费尚不足分尾数。

世界胜利结算使用[任务奖励与世界掉落经济表](任务奖励与世界掉落经济表.md)的实际有限池、级差、精力档、小时帽、每周资格和保底计数；资格空/池空/等级不合格不偷偷抽一次。其`hourId`取服务端胜利结算事件时刻；首领锁`entryWorldCycleId`，稀有锁随机1～4小时刷新形成的`entryWindowId`，不能把两种入场窗口都叫120分钟世界轮回，也不能用入场窗口替代小时额度。小时帽削减、最终发奖、保底推进/消费与源事件ID同commit，不能先发奖再异步扣帽。

教学/预览战斗也有battleId和检查点，但`instanceKind`明确隔离；临时借用技能/装备/药品不进入永久背包、真实学会技能或真实投入账。只有课题完成事件可以推进对应一次任务，不能把教学胜利导入世界掉落或周常战斗奖励。

### 11.1 通知不是资产事务的第二次执行

outbox随业务commit持久写入；`eventId=(commitId,eventIndex)`为稳定事件身份。唯一保管事件另以`(uniqueDomainId,uniqueKey,transitionSeq)`去重，`ownershipGeneration`只在新持有者获得时增加，不代替所有状态迁移序号。公告使用持久`announcementId/announcementSeq`，公开载荷只含审核后的角色名/门派、公开来源和代次，不含accountId或处罚原因。

投递为至少一次，消费者按eventId/公告业务键去重；同一事件允许网络重发，不允许业务重跑。发送后未记已送即崩溃，恢复可再送原事件，不能生成新公告ID。客户端断线重连按已提交游标补状态或取快照；历史公告进未读/传世谱，不当作新获得再播放横幅。是否在线、SSE是否写成功都不能决定发奖是否发生；客户端不能靠ACK请求再次发物。
