## 2. 身份、鉴权与路由

### 2.1 稳定身份与会话

- `accountId` 是账号身份；`characterId` 是角色身份；`worldId` 是所处世界；`saveEpoch` 是该世界本次成长存档世代。显示名、登录名、宅院名和称呼均不是资产、关系或幂等主键。
- M0采用每账号在一个 `worldId + saveEpoch` 内只有一个活跃角色。此限制不是多角色系统的设计承诺；同账号多窗口共享该角色的资产、任务、时间和战斗。M0只用独立测试根/世界的账号库，不接旧v1账号；正式迁移另按存储合同实现与演练。
- 登录建立同源账号会话cookie；角色选择签发不透明的 `characterSessionId`，客户端用 `X-Character-Session` 携带，服务端验证其账号归属及绑定四元组。cookie采用HttpOnly、SameSite=Strict；跨公网必须Secure/HTTPS，M0仅本机HTTP允许Secure关闭。注册/login只校验精确同源Origin及application/json，不要求尚不存在的会话CSRF；其他已登录写请求还须校验会话CSRF令牌。会话秘密不放URL、聊天、SSE正文、持久回执或日志。
- `characterSessionId` 是可撤销的会话凭据，不是characterId。换标签、重新登录或轮换凭据不能另建角色资产或重置事件序号。选角不重用另一个角色的未完成命令队列；退出账号撤销相关连接lease。
- 请求中的 `worldId/characterId/saveEpoch` 只作为与会话相等的护栏，不授予权限；`accountId` 从鉴权得到。目标他人必须传 `targetCharacterId`，再验操作权限；不能仅凭“目标在线”允许扣其钱或接受关系。
- M0采用账号cookie最长7天、角色会话24小时的绝对期限；会话仅内存，届满或重启后重新鉴权，不由heartbeat续期。持久成功登录事实与活会话分开；退出撤当前会话及其lease，不删除同账号其他会话。默认只允许受控邀请注册，无有效邀请配置即关闭；不开放自助恢复/删角接口，不虚构邮件找回通道。密码规则、scrypt参数/认证限流及受控账号恢复读M0实施基线与主数据合同；客户端只读服务端sessionExpiresAt，失效后先重登，再查同一请求回执。
- 账号持久字段account.revision创建为1，wire返回名为accountRevision。真实账号角色链接或持久成功登录事实变化时，每个事务递增1；无变化、原结果重查或仅签发内存会话不递增。authRevision独立控制凭据有效性/会话撤销，不是character.create的并发版本。

### 2.2 有限HTTP路由

除公开meta/health和登录注册外，其余读写都需要账号会话；标“角色”的还需 `X-Character-Session`。JSON请求与响应均声明UTF-8，读响应不缓存私有数据。所有serverTime/expiresAt/deadlineAt及其他绝对时刻均为UTC Unix毫秒安全整数，不传ISO字符串作为权威时间；duration/remainingWaitMs为毫秒整数。HP/MP/XP及银两线缆形状沿主数据合同的十进制字符串/分单位，不降为JavaScript浮点资产。

| 方法 / route | 鉴权 | 输入及作用 | 输出/边界 |
|---|---|---|---|
| `GET /api/v1/meta` | 公开 | 协议协商 | `protocolVersion=1`、可选world、当前saveEpoch、发布阶段、公开manifestVersion；不暴露秘密或隐藏剧情答案 |
| `POST /api/v1/auth/register` | 邀请/注册策略 | `requestId, loginName, password, inviteCode` | 仅创建账号；规范登录名唯一。重复创建不能产生第二account；重试只有验证同一凭据后可取自身结果，不向未鉴权者泄露回执 |
| `POST /api/v1/auth/login` | 登录凭据 | `loginName, password` | 设置账号cookie，返回accountId、accountRevision、角色摘要、sessionExpiresAt、csrfToken；不因名字不存在自动建号 |
| `GET /api/v1/auth/session` | 账号 | 无 | 当前会话与角色摘要；无密码/salt/token明文回显 |
| `POST /api/v1/auth/select-character` | 账号 | `requestId, worldId, saveEpoch, characterId` | 验归属并持久登记本唯一域成功登录事件后签发characterSessionId；登录事件依requestId去重，会话秘密不进回执；不重领bootstrap，不清战斗/任务 |
| `POST /api/v1/auth/logout` | 账号 | 当前会话 | 撤销该账号会话及其角色连接lease；重复退出无额外游戏副作用，不充当撤出副本命令 |
| `POST /api/v1/commands` | 账号/角色，按目录 | 第3节命令信封 | 只执行第4节正式启用的有限命令 |
| `GET /api/v1/receipts/{requestId}` | 原账号及对应角色 | `worldId, saveEpoch, characterId` 护栏 | 自己该世代的终态回执或 `pending/unknown`；unknown不是可换ID重做的证明 |
| `GET /api/v1/snapshot` | 角色 | 当前绑定，无客户端状态 | 第6节一致快照与事件水位；读取不发额外奖励 |
| `GET /api/v1/views/{view}` | 角色 | 第5节有限view及参数 | 分页只读投影；不能借GET交任务、收菜、读后发奖或改变战斗 |
| `POST /api/v1/quotes` | 角色 | 第4节可报价operation及args | 有效期内的费用、输出范围、绑定、前置、对象版本和quoteId；纯预览，不抽出可重滚的实际结果，不扣资源 |
| `GET /api/v1/events` | 角色，fetch读取SSE | `Last-Event-ID` 或 `cursor`，二者同时提供须相等 | 第7节事件流；使用header鉴权，不把凭据塞query |
| `POST /api/v1/presence/heartbeat` | 角色 | `protocolVersion, connectionId, saveEpoch` | `connectionId, serverTime, leaseExpiresAt, saveEpoch`；只续自己的活跃连接lease，不写资源幂等账或增加角色revision |
| `GET /healthz` | 部署规则 | 无 | 仅ready/not-ready、发布版本；不回存档路径、账号、token或管理员能力 |

方法不匹配回405，未知route回404，JSON损坏回400，超过发布配置中的正数体积/频率限制回413/429并给 `retryAfterMs`。M0采用命令JSON上限16KiB；后续聊天120个Unicode字符、称呼6字沿原合同。其他自定义文本按manifest的有限字段长度和名称规则校验，未配置不能默认为无限长。所有玩家文本是纯文本/有类型片段，不回传可执行HTML。

注册是账号建立前的独立幂等域`(worldId, canonicalLoginName, requestId)`，worldId由当前单世界服务确定；规范登录名、非秘密请求摘要、inviteId/邀请消费事实、账号/凭据及注册结果同一持久提交。密码与邀请码明文不进入payloadHash或回执。重试先验证原账号口令与该次原邀请归属，再读取自己的原结果；已消费给本次注册的邀请可用于该次重查，不能因此创建另一账号。不能因原请求已成功、邀请已被它消费而误拒重查，也不能向未通过验证者泄露结果。

历史回执查询例外：GET receipts可以由当前已认证账号读取自己旧saveEpoch/已归档characterId的记录，服务端核验历史归属；这仅是只读查询，不要求旧角色会话仍有效，也不能据此签发旧角色写权限。普通命令/snapshot/events仍严格核验当前角色会话四元组，旧代际不得自动迁入新请求。

登录、选角、heartbeat属于会话控制，不要求伪造角色controlRevision。注册创建账号及选角对应的accountLoginByDomain登录事件须先持久化才成功，后者参与十声90天回收判定；重试同一次选角不能新造登录事件，会话秘密可重新签发。连接lease/会话凭据可以在重启后失效，客户端重登；永久登录史与资源命令不因此获得跳过持久提交的例外。

### 2.3 M0已采用的启用集合与准入

全目录仍为99个业务命令、14个HTTP路由和16个view；登记存在不等于当前阶段全部可调用。M0采用13个路由（第2.2节除POST /api/v1/quotes）、6个业务命令（character.create、cultivation.setEnabled、attributes.allocate、attributes.reset、equipment.equip、equipment.unequip），以及4个view（manifest、character、scene、inventory）。已知后期命令/view及quotes返回PHASE_LOCKED，未知名字按原COMMAND_UNKNOWN/404处理；缺M0必需配置用CONFIG_INCOMPLETE。snapshot只交付当前启用域及明确关闭状态，不用空对象冒充完成后期功能。

M0采用16KiB JSON上限，命令入口每账号10次/秒、burst20；写队列最多1024项、入队等待最多5秒，超限为未受理RATE_LIMITED。认证使用M0主文的独立scrypt队列/账号及IP限制，不在资源写者里等口令计算。SSE每连接待发上限1MiB，超限关闭该连接并按cursor恢复，关闭同时撤其lease；其他有效连接不受影响。上述为已采用准入值，尚未压测；已受理请求不能因等候超时被显示成确定未扣。M0具体身份/数值/随机和运行参数以M0实施基线为唯一入口，后期内容参数与D决定不因此自动获批。

## 3. 命令信封、版本与回执

### 3.1 请求

下面是合法JSON形状示例，ID仅示例值，不是新增内容ID：

```json
{
  "protocolVersion": 1,
  "requestId": "019a0000-0000-7000-8000-000000000101",
  "worldId": "world.demo",
  "saveEpoch": "epoch.demo.1",
  "characterId": "char.demo.1",
  "expectedRevision": 41,
  "expectedObjectRevisions": [{"kind": "item", "id": "item.demo.1", "revision": 3}],
  "command": "equipment.equip",
  "args": {
    "itemUid": "item.demo.1",
    "slot": "weapon"
  }
}
```

| 字段 | 约束 |
|---|---|
| `protocolVersion` | 当前明确为整数1，未知主版本拒绝；新增必填/改义须升主版本。manifestVersion/经济规则版本独立，不能用协议1暗指旧游戏规则 |
| `requestId` | M0采用标准UUID格式，仍是不透明意图键，不要求UUIDv7或按时间排序；同一次意图持久保存在发送队列，超时重发不换。不同意图不得复用 |
| `worldId/saveEpoch/characterId` | 与会话相等；仅character.create的characterId为null，由服务端分配。旧世代请求拒绝，不迁移成新号操作 |
| `expectedRevision` | 非负整数；角色命令比较controlRevision，character.create比较accountRevision。纯泡点数值更新不使本字段冲突；不能用state revision或eventSeq替代 |
| `expectedObjectRevisions` | 对象前置数组，每项kind/id/revision，item/listing/run/invitation/relationship/battle/custody等按命令要求提供；同对象不得重复或相互矛盾。跨对象全部在锁内重验 |
| `command/args` | 只许目录列出的字符串与字段；枚举、数量、ID、嵌套对象均校验。禁止客户端提交经验、概率、奖励包内容、已完成布尔或服务器时间 |
| `quoteId` | 付费/不可逆操作按资源合同需要时放args；报价绑定角色、世代、operation、规范args、对象/规则版本与expiresAt。过期/涨价/输出归属变化必须重新展示，不自动补差价 |

规范payloadHash采用SHA-256(JCS规范信封)，包含协议、身份护栏、command、args、原expectedRevision和expectedObjectRevisions；对象前置按kind/id排序并拒绝重复对象。只包含原请求明示的配置版本/报价引用，不重新混入当前可变服务端配置；不含cookie/header秘密或无意义JSON键顺序。JSON拒重复键、非法Unicode及不安全整数；高精度值用合同字符串，业务名称规范化不由JCS代做。除第2.2节注册专用域外，幂等键统一为 `(actorScope, saveEpoch, requestId)`；actorScope由服务端封装worldId＋accountId（系统动作另用系统域），角色ID在payloadHash里。不能换角色复用请求键；具体存储形状读资源合同。同ID不同payload返回 `REQUEST_ID_CONFLICT`。**先查已存在的同payload终态回执，再推进新意图的时间前置并检查当前expectedRevision**，否则成功后的重发会被自己的新版本误拒绝。

角色保存两个版本：`revision`在真实持久状态变动时增加；`controlRevision`在玩家命令造成真实控制变化或改变可操作资格的结构变化时增加。纯XP/银两泡点累积且未升级只改revision；升级、进战、自动战斗结果、到期资格变化等也改controlRevision。request.expectedRevision比较controlRevision，response.committedRevision返回它，另附stateRevision=revision；heartbeat二者都不改。每个事务每个真实变化的聚合至多递增1；changed=false no-op和业务拒绝只保存回执，不虚增角色/对象版本。不能因2秒tick造成全部操作持续冲突，也不能因此略过当前真实余额校验。

市场成交/关系成立等可同时改多个聚合，返回 `affectedRevisions`（角色带revision/controlRevision，其他对象带自身revision）；客户端不能拿自己的期待版本替别人确认。对象前置统一放顶层expectedObjectRevisions；战斗args.expectedBattleRevision是battle项的同值显式字段，二者不一致拒绝。服务端在同一事务锁内重验全部对象和真实资产，不能先扣买家钱再发现卖方已撤单。

新意图采用固定顺序：入口认证/主体/代际/格式/准入→写者内查旧回执→独立durable时间前置事务（prelude）→最新control/account/object版本→业务commit。prelude采样一次serverTime，结清受影响角色/场景的合法在线段、升级、补期和过期；无实际变化不写空帧，前置失败或未知即停止后续业务。前置造成升级/资格变化可使本次期望版本过期：玩家动作未受理，合法前置收益仍已提交且不回滚，UI提示“修行进度已更新，本次操作尚未执行，请查看最新状态”。旧回执重查不再推进时间；业务提交只改独立草稿，完整帧持久后才发布内存、成功回执和SSE。前置与业务分别真实改变同一聚合时，允许先后各递增一次。

### 3.2 成功及失败

```json
{
  "protocolVersion": 1,
  "requestId": "019a0000-0000-7000-8000-000000000101",
  "status": "committed",
  "worldId": "world.demo",
  "characterId": "char.demo.1",
  "result": {
    "itemUid": "item.demo.1",
    "slot": "weapon",
    "changed": true
  },
  "committedRevision": 42,
  "stateRevision": 108,
  "commitId": "commit.demo.104",
  "affectedRevisions": [{"kind": "character", "id": "char.demo.1", "revision": 108, "controlRevision": 42}, {"kind": "item", "id": "item.demo.1", "revision": 4}],
  "serverTime": 1788847200000,
  "saveEpoch": "epoch.demo.1",
  "replayed": false
}
```

成功HTTP200只表示上述终态已持久提交。`result`是该次操作的结果，不是UI自己推算的余额；完整状态从快照/事件取得。合法幂等no-op可以 `changed=false`，仍有已保存回执；不要求为了no-op虚增游戏资源版本。重试返回原result/committedRevision/stateRevision/commitId，并可标 `replayed=true`；当前状态已更高时不能用旧回执覆盖它。

character.create的主聚合为account，成功回执committedRevision返回新的accountRevision，stateRevision为null；新角色的revision/controlRevision均为1，放在result与affectedRevisions中。不能把新角色的1当作账号提交版本，也不能把账号版本装进角色状态；后续角色命令才比较新角色的controlRevision。

拒绝不声称本次玩家业务发生了资源扣发；它不撤回已经独立提交的prelude收益。auth/格式/限流/revision等未受理拒绝不占幂等键；权威业务校验后的拒绝保存durable rejected终态，并返回保存该拒绝回执的commitId；其committedRevision/stateRevision仍为null，可在error中附当前版本。上面的REVISION_CONFLICT示例属于未受理拒绝，故commitId为null。已存receipt先于时间前置/revision核验，成功后的业务资格不能换键重复领取；已拒绝意图原键重试始终返回该拒绝，条件改变后的新意图可使用新键重新校验。完整终态回执至少保留30天；M0保留全部完整回执/日志，不实施自动压缩，M5才可永久压缩为already_committed/already_rejected、payloadHash、commit/业务结果引用等摘要。旧请求只回摘要并要求resync，不能因明细已压缩再次执行。连接中断/超时/提交结果未知返回或视为 `pending`，不可显示“肯定失败”并重新生成操作。通过receipt查询或**原requestId+原payload**重试查明结果。并发冲突后，先同步；只有用户仍要发起的新意图才生成新requestId与新expectedRevision。

每角色客户端建议串行发送需要状态前置的写意图；在线ACK走独立lease接口，不承担资产计算。双窗口同时写仍由服务端版本/幂等处理。任何前端乐观动画均可撤销，不能先增加永久物品或显示稀有掉落，再等保存结果。

### 4.4 一个行动机会的唯一身份

服务器给当前行动角色下发 `battleId, battleRevision, opportunityId, actionId, deadlineAt`。`opportunityId`标识本角色这次行动机会；`actionId`是此机会唯一待决定槽，由服务器生成，客户端不能用另一requestId再占一个槽。请求包含 `expectedBattleRevision` 与这两个键。

```json
{
  "battleId": "battle.demo.7",
  "expectedBattleRevision": 12,
  "opportunityId": "opportunity.demo.7.6",
  "actionId": "action.demo.7.6",
  "action": {"kind": "skill", "skillId": "skill.sl.dali_jingang_zhi", "targetIds": ["combatant.demo.foe.1"]}
}
```

`kind`有限为basic、skill、defend、item、flee。item还需服务器已准许的itemRef；不存在“战内另发consumable.use再免费施招”。目标由当前battle的combatantId限定，怪物模板ID不能代替本局敌人实例。多段/连锁/反击及多目标的后续由引擎按合同决定，不让客户端拆成多次起手。

手动、自动、超时和控制跳过争用同一actionId。胜者决定动作后，迟到请求回 `ACTION_ALREADY_RESOLVED`及本人可见既有动作摘要；新requestId也不能抢回已经执行的机会。回执含acceptedActionId、最新battleRevision及checkpointId。checkpointId只标识最后持久状态，不是可供客户端选择的回档位置；实际保存与随机推进读资源合同。手动输入窗口按时钟表本轮提案10000ms，deadlineAt由服务端给出；重启按最后检查点剩余等待重排且保留actionId，不新增回合动画速度。每个承伤事件先结致命保护，三波/层主/整局的结算边界不由UI动画完成回调触发。

## 6. snapshot与revision的共同屏障

快照建议至少返回：

```json
{
  "protocolVersion": 1,
  "worldId": "world.demo",
  "saveEpoch": "epoch.demo.1",
  "characterId": "char.demo.1",
  "revision": 107,
  "controlRevision": 41,
  "manifestVersion": "manifest.demo.1",
  "projectionVersion": 1,
  "streamId": "stream.demo.char1.epoch1.p1",
  "eventSeq": 106,
  "cursor": "stream.demo.char1.epoch1.p1:106",
  "serverTime": 1788847199000,
  "state": {"character": {}, "scene": {}, "capabilities": [], "pendingReceipts": [], "activeBattle": null, "activeRun": null}
}
```

state中的空对象仅展示信封结构，实际字段由主数据合同/上述views定义，不能据此发布空面板。

`streamId`稳定绑定 `(worldId, saveEpoch, characterId, projectionVersion)`，不随connectionId、标签页或重新登录改变。`eventSeq`是这个私有投影流中的连续递增整数，和revision/controlRevision/世界commit顺序不同：一次commit可生成多个事件，一条面向本人的世界公告也可不改变角色资源。

获取快照时必须在同一屏障得到状态与该状态覆盖的eventSeq。若已有持久commit尚未扇出本人投影，先补投影到该commit再取水位；也可由实现采用明确定义的commitSeq过滤，但不能返回“最新状态＋更后的无关水位”而吞掉尚未投递的通知。屏障后的所有本人可见事件必须有seq大于快照水位，且可补读。

快照同时包含未读重要通知的索引/数量与messages分页起点；包含在屏障之前的通知不能只靠后续SSE送达。客户端装快照时读取这些持久通知，即使对应outbox已扇出但从未真正到过这个设备，也能查到原事件。

客户端先装快照，再用cursor接流；不能先清空旧状态后仅接“从现在开始”的事件。权威状态按revision应用；命令并发前置单独跟进controlRevision。一次带多个域的事件先检查本地baseRevision再原子应用。若本地版本不匹配，停止应用增量并补快照，不能拼成一半旧背包、一半新银两。

## 7. SSE、连接与重连

### 7.1 帧和有限事件名

持久事件使用标准SSE的id/event/data字段，例如：

```text
id: stream.demo.char1.epoch1.p1:107
event: state
data: {"protocolVersion":1,"eventId":"event.demo.104.state","eventSeq":107,"streamId":"stream.demo.char1.epoch1.p1","saveEpoch":"epoch.demo.1","commitId":"commit.demo.104","committedRevision":42,"stateRevision":108,"serverTime":1788847200000,"payload":{"baseRevision":107,"revision":108,"controlRevision":42,"changedDomains":["inventory","character"]}}

```

`eventId`是服务器持久唯一事件身份；`eventSeq`只负责该可见流排序。广播同一个eventId可投到多个角色流，各自seq不同。服务端投递至少一次，客户端按eventId去重、按seq推进cursor；重复投递不得重放奖励动画或增加数量。永久奖励/成就/师承/唯一武器等领域事件身份和去重记录不能因outbox已发送或24小时窗口过期而删除。

| event | 收件范围 / payload最少内容 |
|---|---|
| `state` | 本人；结构域替换/变化后的快照、baseRevision/revision，不让客户端自行补算经济 |
| `vitals` | 本人；同一提交后HP/MP/XP/银两/精力与revision，使用精度合同；不反向改controlRevision，不得把未保存预测值冒充权威余额 |
| `command` | 本人；requestId及终态回执摘要/receipt链接，用于HTTP丢失后的确认 |
| `chat` | 发送时授权的世界/场景/门派/私聊接收者；messageId、发送时名字/标记快照、纯文本 |
| `scene` | 当前可见场景；成员/占位/可达变化，不发他人背包或私有战斗日志 |
| `combat` | 参战者及该玩法明确允许的观察范围；battleRevision、opportunity/action/checkpoint、可见日志；默认个人流 |
| `quest` | 本人；实例/目标/待领/已领变化，教学借技与正式learned分开 |
| `inventory` | 本人；uid/数量/归属/锁定变化及revision，不多开第二资产账 |
| `market` | 公共列表变化与各自私有成交回执分开；公共部分不带买卖双方余额 |
| `relation` | 关系当事人；invitation/relationship版本、接受/拒绝/解除及展示变动 |
| `mail` | 收件人；持久messageId和未读变化，私信内容不广播 |
| `collection` | 本人达成/发布分母变化；全服首个另发一次broadcast |
| `home` | 主人生产/库存事件；访客仅公开宅名等展示变化 |
| `dungeon` | 本人；runRevision、已揭示选择、可恢复/结算状态，不广播未知节点 |
| `ten_echo` | 本人候选/保管回执或公开传世谱变更，敏感份额只发本人 |
| `broadcast` | 合法全服公告：结拜/出师/唯一武器/首个等已提交结果；不借公共公告提前发布私有随机抽签 |
| `rare` | 出现时该场景合格在场者；不是全图稀有雷达；补读仍只给原合法接收者 |
| `config` | 本人可见manifest/协议/阶段变化；已开始实例继续按自己的规则快照，变更不能重滚进行中奖励 |

`state/vitals/各领域事件`可能描述同一commit，客户端按revision替换而非反复累加。服务端可以合并尚未投递的高频状态显示，但不能跳过其间独立命令回执/奖励/关系通知；同一eventSeq不得在不同重试中改payload。

连接控制帧为 `connected`、`snapshot_required`、`session_expired`、`world_reset`，没有可当奖励处理的eventId。connected给connectionId、当前serverTime、leaseExpiresAt与流身份；注释keepalive只保链路，不延长在线资格。客户端每5秒发送一次已鉴权heartbeat，服务端lease10秒；SSE关闭立即撤该连接lease，最后一个有效lease消失时按时钟合同停止公共修行。多个连接时间取并集，不多发日常、人数加成或交情。

### 7.2 恢复顺序

1. 暂时断线保留最后成功应用的cursor、未确认requestId/原payload和本地显示缓存；不得存“准备给多少奖励”作为恢复依据。
2. 会话仍有效时携最后cursor重连，服务端验streamId/世代/投影版本；只补 `eventSeq > lastAppliedSeq` 的本人事件，已发未ACK可重复。
3. M0采用事件补读窗口24小时，底层完整日志保留不扩大这个对外窗口。游标早于窗口、未知/超前、不属于本人、projectionVersion改变时返回 `snapshot_required`；不能默默只补最新一条。完成全量后，从其新水位继续，并分页读当期已启用领域的日志、通知/回执。
4. 世代改变返回 `world_reset`/`SAVE_EPOCH_MISMATCH`，关闭旧连接，丢弃旧世代未发送写队列；旧请求只能按主合同查询历史回执，绝不对新角色自动重放。
5. 补读完后逐个查询未确认请求。HTTP成功但SSE未到，以已持久回执为准；SSE先到但HTTP丢失，不再做第二次操作。网络未知与业务拒绝在界面分开。
6. 世界PvE/切磋继续自动接管、古墓冻结/24小时恢复及生产成熟按时钟合同；重连本身不扣入场费、不补离线泡点、不清CD或恢复HP/MP。

连接慢于消费时服务端可关闭该连接并要求从cursor补读，不能无限堆内存；关闭不等于取消已提交命令。SSE流身份不能作为授权，当前cookie和characterSession仍须有效。退派/隐私变化后的新事件先验收件权限再分配本人seq；不能让被过滤事件造成客户端误以为缺帧。补读仍重新验当前可见权限；若待补事件已不可见，不修改同eventId的原payload伪装另一事件，也不发秘密后让客户端隐藏，而是发snapshot_required并改用合法快照/过滤日志恢复。已撤权限不会被旧SSE恢复；不向新订阅者补发他本不应见的旧私聊。

## 8. 有限失败码与恢复动作

error字段可附本人的currentControlRevision/stateRevision、合法requiredLevel、blockingId、retryAfterMs；不附他人私有余额、密码摘要、内部SQL或存档路径。message是玩家可读解释，客户端按code/recovery处理，不匹配中文句子猜成功。

| code | HTTP | 含义 / 恢复 |
|---|---:|---|
| `INVALID_JSON` / `INVALID_ARGUMENT` | 400 | 格式或有限参数不合法；修改输入，不自动重试原坏请求 |
| `PROTOCOL_UNSUPPORTED` | 426 | 协议主版本不支持；更新客户端 |
| `UNAUTHENTICATED` / `SESSION_EXPIRED` | 401 | 重新登录/选角，再查原requestId |
| `FORBIDDEN` | 403 | 当前身份无权操作；不借换显示名或目标ID重试 |
| `SUBJECT_MISMATCH` / `SAVE_EPOCH_MISMATCH` | 409 | 会话/角色/世代不同；重新取绑定和快照，旧意图不自动迁移 |
| `COMMAND_UNKNOWN` / `CONTENT_UNKNOWN` | 404 | 命令或可见内容ID不存在；不执行近似同名条目 |
| `FEATURE_DISABLED` / `PHASE_LOCKED` | 409 | D未启用或当前M阶段未开放；显示决定/阶段原因 |
| `CONFIG_INCOMPLETE` | 503 | 必需价格/目标/规则未齐；不免费执行或自己取默认值；待配置修复后新意图 |
| `SNAPSHOT_REQUIRED` | 409 | 游标不在窗口或不匹配当前投影；全量及日志/通知补读后接新cursor |
| `REQUEST_ID_CONFLICT` | 409 | 同ID不同payload；禁止改旧请求蒙混重试 |
| `REVISION_CONFLICT` / `OBJECT_REVISION_CONFLICT` | 409 | 本人或挂单/关系/装备/战斗版本已变；读最新状态再决定 |
| `PRECONDITION_FAILED` / `LEVEL_REQUIRED` / `LOCATION_REQUIRED` | 422 | 前置、等级或地点不满足；返回允许公开的缺项 |
| `STATE_LOCKED` / `INSTANCE_ACTIVE` | 409 | 战斗、托管、生产或在途副本锁；按当前实例完成/恢复，不伪造空状态 |
| `INSUFFICIENT_RESOURCE` / `CAPACITY_EXCEEDED` | 422 | 余额/材料/MP不足或容量满；不部分扣资源 |
| `BOUND_ITEM` / `INCOMPATIBLE_ITEM` / `TARGET_INVALID` | 422 | 绑定、槽位/技能兼容或目标不合法；按公开约束改选 |
| `QUOTE_EXPIRED` / `QUOTE_CHANGED` | 409 | 重新取得并展示报价；禁止自动接受更高价或不同绑定 |
| `QUOTA_EXHAUSTED` / `COOLDOWN_ACTIVE` | 422 | 真正需要额度的操作不足；返回本人周期/下次可用时间，不补调试额度 |
| `ALREADY_CLAIMED` / `ALREADY_UNLOCKED` | 409 | 别的意图已经领取/解锁；返回本人原结果引用，不能再扣费 |
| `ACTION_ALREADY_RESOLVED` / `OPPORTUNITY_EXPIRED` | 409 | 当前机会已有动作或已过期；接最新battle，不能补打一招 |
| `INVITATION_EXPIRED` / `INVITATION_DECLINED` | 409 | 关系/切磋邀请终态；不把别人拒绝当暂时失败反复自动邀请 |
| `RATE_LIMITED` | 429 | 按retryAfterMs等候；不消耗游戏资源，不能以多窗口多算在线 |
| `COMMIT_PENDING` / `UNKNOWN_COMMIT_STATUS` | 503 | 尚不能确认提交结果；查receipt/原ID原payload重试，不换ID再次付款 |
| `STORAGE_UNAVAILABLE` | 503 | 持久层不能给确定成功；按提交状态恢复，不先发物品/SSE成功 |
| `INTERNAL_ERROR` | 500 | 给可追踪errorId，恢复仍先查原receipt；不假定异常前绝无提交 |

世界成品周资格用尽时，合法普通战斗仍可开战并按其余合法通道结算；这类**奖励通道禁用原因**放在lootEligibility/result，不误用QUOTA_EXHAUSTED封死基础PvE。精力0同样只是收益档，不能拒绝全部战斗。完整古墓次数不足才拒绝创建新run，既有run恢复不需要第二份次数。
