## 1. 当前源代码与目标合同分开

只读基线为隔离审计工作树的`0960410`代码，下面是本轮读源码确认的事实；历史测试结果仍见[缺口审计](首版开发缺口审计.md)，本轮不重新声称跑过它们。

| 现状依据 | 真实行为 | 第5项目标 |
|---|---|---|
| [HTTP](../server/http.js) 的 `/api/login`、`/api/cmd`、`/api/events` | 登录凭据/玩家用名字关联；命令处理后可能不论业务结果直接返回`ok:1` | 新协议明确认证、角色会话、成功/拒绝/结果未知和已提交回执，旧接口不是新协议别名 |

| [存储](../store.js) 的`doFlush` | 在途写复用promise；JSON同步路径与外层`flushing`赋值存在先前已复现的后续写停滞问题 | M0修复和回归仍必需，本轮没有修复代码 |

| 旧版本文 | Map/Set示意、五分钟内存nonce、按名字拼关系键 | JSON安全形状、稳定身份、持久去重和唯一关系行 |

M0采用独立v2单Node进程、HTTP＋SSE＋POST命令及**单写者、事务日志与快照**文件后端，版本和隔离路径见M0基线；MySQL须满足相同原子与回放合同后才能切换，不因已有mysql2依赖就宣称两后端已等价通过。

## 2. 身份、版本和精度

### 2.1 稳定身份

| 字段/键 | 类型与所有者 | 约束 |
|---|---|---|
| `accountId` | 服务端随机稳定ID，账号库 | 不随显示名/世界清档改变，不由请求传入的名字授权 |
| `characterId` | 服务端ID，角色 | M0采用每账号每`worldId+saveEpoch`至多1个活跃角色；删角不复用ID，重建/清档不复制旧资产 |
| `worldId` | 稳定逻辑世界ID | 区别正式/内测世界；跨世界引用默认拒绝 |
| `saveEpoch` | 世界进度代际ID | 普通重启/快照不变；清档或有意回档使旧请求失效。不是每天刷新键 |
| `uniqueDomainId` | 唯一武器域 | 十声唯一性跨分线/角色，按既有合服与保管合同；不是客户端房间名 |
| `uid / battleId / runId / listingId / qualificationId` | 服务端独立ID | 标识真实实例、交易/战斗或资格；永不由数组下标/名字充当 |
| 内容ID | 第3项稳定字符串 | `equip.*`是模板，`uid`是实例；182任务、50技能、45材料等由内容注册读取，不自由拼接生成 |
| `bondPairId` | 世界代际＋两个characterId有序元组 | 作为两人关系唯一索引；显示名可变，不能用`甲\|乙`拼接做身份 |

M0已采用单角色限制，不减少四故乡、十派或永久散人可选项。一个角色允许多连接看同一状态；所有连接共享资格/钱包/时钟，不能每窗口生成一份角色。账号在同一唯一域的活动和师承终身关系另按accountId记录，不能靠重建角色增加终身权益。

### 2.1.1 M0采用的账号流程与后续迁移

默认使用受控邀请码注册；账号cookie最长7天，角色会话最长24小时，过期重新鉴权并建立新的持久登录事件。单次网络重连/heartbeat不算新登录，不因此延期；持有唯一武器的人长期正常登录不会因同一不失效会话超过90天而误回收。服务器给明确sessionExpiresAt；用户退出立即撤销该会话。

新密码按Unicode原文校验，不截断/去首尾空格，采用长度12～128个Unicode码点且UTF-8不超过512字节；旧密码只保留legacy验证兼容，成功验证后升级摘要。新登录名采用3～24个ASCII字母/数字/下划线，统一小写作唯一键；旧名通过一次迁移映射保留，不能擅自改名致无法登录。显示角色名与登录名分开，新显示名2～12个Unicode字符、纯文本，本世界活跃角色名唯一，历史事件保留当时名；规范化与重名检查由服务端统一。M0已采用上述长度；角色名先NFC、按码点计数，拒绝控制字符/孤立代理项与首尾空白。邀请消费、注册重查、scrypt、会话/CSRF的确定规则见M0基线§3；旧账号迁移在M5前另做转换与演练，M0只使用新测试账号。

首发不开放普通客户端自助删角、跨账号转资产或无身份核验的找回接口。账号找回/封禁/删除采用受控人工流程：核验原注册邀请与既有账号归属证据，记录操作者与原因；证据不足不移交账户。凭据重置递增authRevision、撤旧会话并保留全部已提交资产。删除前收束进行中战斗、订单、挂单、待领、关系与唯一保管，留终身去重/历史墓碑；删除申请本身不发新号奖。此处只是流程合同，不执行真实账号操作；后续新增自助入口须先补验证与验收。

### 2.2 四种不同的版本

- `schemaVersion`：存档形状版本；不支持的较新版本拒绝写入，不能补默认值后覆盖。
- `contentVersion / economyVersion / combatVersion / mathVersion`：不可变配置快照标识及摘要。已接任务锁奖励版本，战斗锁技能/装备/随机版本，订单锁配方/报价；显示名更新不改ID。停用配置须仍可结清旧订单。
- `revision`：聚合每次真实持久变化的单调安全整数；新账号/角色均从1起，no-op不增、溢出停写；`character.controlRevision`只在玩家操作或影响可操作资格的结构变化时推进。纯XP/银两泡点且未升级只推进`revision`；升级、进出战、装备、任务达成、资格变化推进两者。
- `commitId / commitSeq`：一次存储提交的身份/全局顺序；`eventSeq`是投递到某角色视图的事件顺序。两者与角色revision不能互换。

命令的`expectedRevision`比较当前角色`controlRevision`，成功的`committedRevision`返回它，同时给`stateRevision`；物品、挂单、run等另比较`expectedObjectRevisions`。所有金额/资格仍在单写者内按最新值校验，不接受客户端余额覆盖。由此避免每2秒小额泡点让所有操作持续冲突。没有角色的账号命令使用账号revision，精确定义见协议表。M0创角以账号为主聚合：committedRevision返回新accountRevision、stateRevision=null，新角色revision/controlRevision=1放result/affectedRevisions；真实账号链接/持久成功登录事实每事务+1，authRevision独立。

### 2.3 可序列化数值

| 值 | 存储形状 | 处理 |
|---|---|---|
| 等级、点数、CD、层数、次数 | JSON安全整数 | 非负及各自上限校验；不用浮点表示半次资格 |
| 永久银两 | `silverMinor`为非负十进制整数字符串，单位0.01两；`silverRemainder={numerator,denominator}`为精确有理尾数，两值为整数字符串，单位分且0≤n<d | 1两=100分。支付整分，连续收益先累积尾数；不保留另一份gold或两余额 |
| 本级XP | xp固定18位＋有符号约分xpRemainder，单位XP | 权威X为两者之和，HALF_EVEN投影尾差≤半个18位量子；升级读X，不读投影 |
| 当前HP/MP | 18位投影＋hpRescaleAnchor/mpRescaleAnchor | 比例锚点保留最近真实资源事件；纯上限变化从锚点精确重算，不逐次取整回写比例 |
| 盾、其他比例与积分 | 非指数十进制字符串；默认小数18位 | 独立Decimal50有效位HALF_EVEN；逻辑事件边界才落18位，显示值不反算 |
| 时间 | UTC Unix毫秒安全整数 | 只读服务端权威时钟；日/周键按Asia/Shanghai另算，不能从本地化时间字符串排序 |
| 无序集合 | 去重字符串数组，规范排序 | 不存Map、Set、undefined、NaN、Infinity、BigInt字面量或函数 |

M0锁decimal.js 10.6.0、50位计算/HALF_EVEN及mathVersion=m0-decimal50-rational-v1；XP精确余量见时钟§2.3，HP/MP比例锚点见属性§6，不能简化成只存18位。本文不安装依赖。比例的精确有理常量保留分子/分母，整数概率可按固定整数权重抽；世界保底每次1/0.30可用整数百分单位100/30表示，门槛1200/800/1200。HP/MP正值不因显示0.00判死；多段攻击必须每个伤害事件先做致命判断，不能等整招结束。

银两尾数必须约分：分母>0、gcd(n,d)=1、0≤n<d，零固定`{numerator:"0",denominator:"1"}`。由整数时间/价格或有限十进制配置精确转成分数后计算，不先经binary Number或18位舍入再转分数；每次把旧尾数与精确收入相加，floor所得整分加silverMinor，剩余约分。例L1每2秒收入25/3分，连续三次为8分+1/3、16分+2/3、25分+0；12次恰好100分。所有整分支付只校验/扣silverMinor，保留原尾数，不把不足1分当可支付资金。这个特例保证最小支付单位不因循环小数逐tick少发；XP与HP/MP分别使用上述余量及比例锚点，不能仿照银两的非负尾数范围。

绝对UTC时间戳/日周边界仍是整数毫秒；连续积分内部的升级临界偏移可保存为`{numerator,denominator}`有理毫秒，不能先四舍五入升级时刻再计算新H的银两。内部偏移来自本mathVersion锁定的十进制XP输入/速率转精确有理数，段端点不越过该次实际有效区间；角色可操作资格只在包含该段的事务提交后对外可见。精确银分只保证对已锁定的实际积分段无支付截断损失，不宣称XP理论曲线、伤害或全部无理数公式无限精确。改变真实速率时按边界分段，存/读文件不另加边界。

连续积分保存区间、速率版本、已累计高精度值和未支付尾数；换景/升级/05:00/自然小时等真实规则边界才分段。保存文件、重连、读取界面不是新的计算边界，不得多舍入或重发尾数。每行动内部反应链用工作副本处理，持久化整个合法行动检查点；崩溃回到前一已提交检查点时使用同一随机计划，而非再掷不同结果。

### 3.1 装备、材料和容量

装备`holder`是唯一位置真值：`equipped(characterId,slot)`、`bag(characterId)`、`marketEscrow(listingId)`、`delivery(ownerId,deliveryId)`、`worldCustody(uniqueDomainId)`或`retired`。角色六槽映射与行囊列表是索引/视图，重建后必须恰好一处；同槽最多一件，退休uid不能重用。战斗用快照引用不改变容器，`activeBattleRefs`另记。

材料按`characterId+materialId+bindingOwner`分量记数量/锁定量；总量是分量求和视图，不能另写`p.mats`又写home仓。前文`p.mats`在新版只代表这个统一账本接口。默认优先绑定份额；指定仅用可交易料时不足拒绝，不能静默使成品绑定。

M0采用普通装备行囊容量48件，已装备六件、材料/种食/门票不占装备格；不附收费扩容。第4项原矿50、种子/食物各32、摸金令8等上限保留。系统付费生成先预留目标容量；自选先占待领奖资格、实际生成在领取时。已经不可逆提交的随机掉落或归还物品若无法放入行囊，转`delivery`保存同一资产，不重新抽/变现/丢弃。配送仓只收系统已挣/归还，不允许玩家主动存入；待领资产计拥有权、可查询，不可直接穿/交易。容量与是否允许继续领新随机装备必须显示，第6项验证不会形成隐形仓库升级收费。

### 3.2 任务与课程

一次任务按原ID保存`status=available/active/objective_satisfied/reward_pending/completed`及证据，所有判断结果附内容版本和服务端事实来源。各故乡并不生成可领取的另三条主线；角色只走35步。《姑存》案卷的已确认/传闻/推测分开、动态人物名保存显示快照，但身份仍用npcId/actorRef。

教学保存`lessonInstanceId、taskId、borrowedSkillIds、objectiveState、checkpoint`；借用技能只存在教学快照，最终一次提交才写正式learned以及对应reward键。学习等级10/18/26/38/50不被帮贡、装备或技能排序绕过。技能和天赋保存已点/已学事实，装备临时增级进入计算快照，不反写learned。

日常`qualificationId`首次接受锁定level/E/H/version；换题保留锁定值。首次目标满足写`completedAt/completedLevel/completionDayId/completionWeekId`与`TaskObjectiveSatisfied`，领取另写`rewardGrantedAt/awardWeekId/rewardCommitId`。周票只看前者≥40及原完成周，WQ日常推进只看后者及事件前已存在的WQ资格。目标39级完成、40级领不补票；04:59完成、05:01领不把已挣票移到新周。已完成资格不能取消清空完成标记重刷。

### 3.2.1 天赋洗点的缺参补齐

F10已保留自由混点与洗点，旧天赋文没有洗点费用/次数合同。本轮建议：**战斗外且无活跃古墓run，天赋洗点免费、无每日次数**；只退回本角色实际已投入的天赋点，不增加每6级1点/最多10点的总资格，不改已学技能、派别或毕业事实。可清零后暂存未分配点；无分配时返回changed=false。

持久保存所选talentId及投入等级、未分配数和talentAllocationRevision；提交时按当前等级、派别、层级与原天赋依赖校验新配置，全量原子替换，不能先退点再部分点入不合法分支。四维与天赋是分别操作，不顺带重置另一项。派生maxHP/maxMP变化沿属性合同保持当前比例、死亡仍0，不免费回满、不产生新战斗资源；已有battle/run只使用开战快照，因此活跃run不允许借冻局换天赋。此推荐不宣称已通过平衡验证，也不新增洗点材料或来源ID。

### 3.3 战斗与run检查点

开战快照包括参与者/阵营、等级/天赋/装备uid版本、resolvedWeaponFamily、完整skillOrder/skillRankPriority、技能等级预算、敌人模板与行为版本、模式/奖励资格、费用与随机计划。动态资源、控制、护盾、DOT、反击次数、CD及冷却推进名单、本人机会计数、延迟触发快照保存在同一battle聚合，不能只存HP/MP。

每个主动行动及完整反应链是一个提交单元；内部每伤害事件先判断保护/死亡再继续，回合末同样经过完整事件链。`actionId/stepSeq`不复用，已持久化的机会不可因重发skill再次消费。行动随机种子在开战/动作受理时确定，step推进同结果一起保存，重启从检查点续用。失败或配置不支持时冻结待恢复，不用当前角色重新开局。

世界PvE与双方同意切磋断线按锁定策略继续，不靠断网暂停；服务器停服不补过了多久就打多少回合。古墓单人局断线按既有24h冻结，真实食物锁、临时装备、节点与入局周仍保留；精确规则见时钟及资源合同。

## 5. 查询投影、推送和内容版本

命令只传操作意图和目标ID；服务器生成价格、奖励、随机结果、归属和角色版本。SSE保留state/vitals分包意图，改用明确版本与字段集合，废除按排除JITTER字段猜“结构是否变化”。快照来自已提交聚合，带revision/controlRevision及一致游标；增量是带版本的绝对值/明确操作，重复事件不能重复加银两。

个人stream按worldId/saveEpoch/characterId/projectionVersion稳定，token轮换不生成第二套资源事件。可补传窗口推荐24h；超窗先发snapshot_required再取全量与持久通知/战斗记录。十声取得、首个、出师等永久历史和outbox业务去重不随SSE窗口删除。私聊/门派/场内事件有明确收件人集合，并在补读时重新验可见权限，不能用用户传入的characterId订阅别人。

每次配置发布保存不可变manifest：schema、featureGate、内容ID集合/摘要、经济/战斗/math版本、正式/内测标签。未知装/材不改成普通白装或0，原记录连同原版本隔离；资产持有人保留证据，禁止出售/消费这项，其他无关角色可继续。未知活跃battle/run或唯一登记冲突时冻结对应功能，恢复所需旧配置缺失属于发布阻塞。

## 6. 进入实现与第六项验收的衔接

本轮已规定数据归属、版本/精度、协议/事务/时间、可序列化示例与恢复步骤。M0仍须实现单写提交、幂等、账号与投影；实际旧档迁移/生产恢复在M5前完成演练，并按三个分表及存储方案的故障矩阵验证；不能把字段齐全当作数据库或API已存在。
